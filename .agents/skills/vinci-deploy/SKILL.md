# Deploy a team install

The human guides in `docs/install/` are the single source of truth for commands. This skill says what to ask, in what order to work, what never to do, and how to prove each step. Read the guide section named in each step and run its commands as written; when a command fails or its output differs, use the "If it differs" notes there and `troubleshooting.md` before improvising. When you fix a guide's command, fix the guide too.

## Ask first

Ask the human for everything below before touching anything, in one message. Don't guess any of it.

| What | Example | Used for |
| --- | --- | --- |
| Server address and how to reach it | `root@203.0.113.10`, key file or SSH options | every server step |
| Team hostname, and whether it already points at the server with ports 80 and 443 open, or needs the optional Cloudflare Tunnel (then the Cloudflare zone and object name) | `acme.example.com`; `example.com`, `vinci-acme` | install steps 5 and 6; the tunnel name must start with `vinci-` |
| Only for the tunnel: where the Cloudflare API token is (Tunnel: Edit, DNS: Edit) | `op://<vault>/<item>/credential` | read inside each command that needs it |
| People: id and email each | `alice: alice@example.com` | `users.yaml` |
| First admin of the admin panel (need not be one of the people; admins are fully trusted) | `admin@example.com` | `admins:` in `users.yaml`, `HUB_ADMIN_EMAILS` (the same email in both) |
| Model keys: provider and where they are, or none. Keys can also be set once in the panel's Global settings → Models, which copies them to everyone | `ANTHROPIC_API_KEY` from `op://…` | `.env` or Global settings |
| For a change: the image tag in use | `VINCI_TAG` in `/opt/vinci/.env` | upgrades and teardown |

If the token read fails (1Password prints `authorization timeout`, the script says `CLOUDFLARE_API_TOKEN is unset or empty`), ask the human to unlock their password manager. Never ask them to paste the token or a password.

## Safety rules

- **Never print secrets.** Not the API token, `TUNNEL_TOKEN`, `PROVISIONER_TOKEN`, `API_INTERNAL_TOKEN`, `API_APP_KEY`, passwords (`vinci:user` prints one once: tell the human it is in the output, never repeat it), model keys, `/opt/vinci/.env`, `/opt/vinci/admin-password`, `auth.json`, `models.json` with keys, or backups. Read tokens inside the command that uses them (`CLOUDFLARE_API_TOKEN="$(op read '…')" bun …`); never export them in a shell profile, write them to a file, or put them on the server. The only Cloudflare secret the server holds is `TUNNEL_TOKEN`, with the tunnel, in `/opt/vinci/.env` (mode 600). Never put the install token on the server. Hide emails in anything you post publicly.
- **Tunnel objects only through the script.** Only `bun scripts/deploy.ts cloudflare apply` creates the tunnel, its route and its DNS record. Never create them by hand or in the dashboard. Vinci has no Cloudflare Access any more: never create an Access app in front of an install (it would ask for an email code before the Vinci login).
- **Exact-name ownership on Cloudflare.** The tunnel is `vinci-<team>`; its DNS record carries the comment `vinci deploy vinci-<team>`. Accounts hold unrelated objects with similar names: never change or delete anything by prefix or by hand. Before `cloudflare destroy --yes`, run it without `--yes`, read every listed line, and check each names `vinci-<team>` or `<team>.<domain>` exactly.
- **Never clean Docker host-wide.** No `docker system prune`, `docker volume prune`, `docker image prune`, `docker network prune` or `docker builder prune`. Remove only objects you created, by name: `ghcr.io/meetvinci/vinci-<image>:<tag>` images, `vinci_data-<id>` volumes after a confirmed purge, containers you started for tests.
- **Data deletion needs the human's yes.** `bun deploy.ts purge <id>`, `docker volume rm`, deleting backups, `rm -rf /opt/vinci` and `cloudflare destroy --yes` are irreversible: list what goes and wait for confirmation.
- **Never touch the firewall's chains or the host's `INPUT` policy by hand.** The `firewall` service owns `VINCI-DAEMONS` and `VINCI-DAEMONS-HOST`, puts them back within 2 s and then reports unhealthy for one check (`bun deploy.ts firewall status`); open an internal destination only through `VINCI_INTERNAL_ALLOW` in `.env` and only when the human names it.
- **Linux only.** Isolation between people is Docker Engine's per-network rule. Never run a team on OrbStack or Docker Desktop, and prove isolation on the real server.
- **Images come from GitHub Container Registry**: `ghcr.io/meetvinci/vinci-<image>` is public, so the server pulls with no `docker login` and no password (release tags `vX.Y.Z`, `main`, or a full commit built by the **Images** workflow; `admin.md` "Images from CI"). `unauthorized` or `denied` means a package is still private: tell the human, an org owner changes it; never work around it with a login. Releases up to `v0.1.7` are only in the old private registry; an install still on it moves as `admin.md` "Images from GitHub Container Registry" says. Only for a commit CI has not built, build off the server on the admin's computer (`bun run build:images`), load over SSH and set `VINCI_REGISTRY=` empty. Never build on the server.
- **Don't attach anything to `vinci_user-<id>`, `vinci_sandbox-<id>` or `vinci_provisioner` networks**, and don't pair your own device into a person's Vinci: a device paired there can act as that person. The provisioner holds the Docker socket: never publish its port, give it capabilities, or let anything but the hub reach it.

## Install

Follow `docs/install/install.md` steps 1 to 9 in order. Stop at the first failed check and report it.

| Step | Proof it worked |
| --- | --- |
| 1. Check the server | `x86_64`, Ubuntu 24.04, `avx2`, at least 3.7 GiB memory, 40 GB free (`bun deploy.ts check` once Bun is there: a later Ubuntu or 30 to 40 GB free is a warning, fine only for a test server) |
| 2. Docker | server version 26 or newer, `docker compose version` works, service `enabled` |
| 3. Images and files | seven `ghcr.io/meetvinci/vinci-<image>:<tag>` pull lines (or, for an unreleased commit, `amd64` for all seven local images and seven `Loaded image:` lines); `/opt/vinci` mode 700 with the five files; `.env` mode 600; `bun --version` on the server |
| 4. `users.yaml` | one `<id>: <email>` per person under `users:`; the first admin under `admins:` |
| 5. Hostname | `dig +short <host>` gives the server; ports 80 and 443 open. With the tunnel instead (install, "Optional: Cloudflare Tunnel"): `created` or `unchanged` for the tunnel, route and DNS, `cloudflare.env` written (git ignores it) and merged into `.env`, then deleted |
| 6. Login secrets | `COMPOSE_FILE` with `caddy.compose.yaml` (and `cloudflared.compose.yaml` after it with the tunnel), `VINCI_PUBLIC_HOST`, `API_INTERNAL_TOKEN` and `API_APP_KEY` generated on the server, never printed |
| 7. Start | `HUB_ADMIN_EMAILS` set and `1` from the `PROVISIONER_TOKEN` check; `Applied <n> users: … (and the template workspace)`; every container `(healthy)`, Caddy, the API, PostgreSQL, the provisioner, `vinci-daemon-template-1` and every `vinci-sandbox-<id>-1` included, `bun deploy.ts status` exits 0, and `bun deploy.ts firewall status` says `healthy`; with the tunnel, `Registered tunnel connection` in the cloudflared log; the first admin's login made with `vinci:user` |
| 8. Check | `/rpc` and `/admin` 302 to `/auth/login`, `/favicon.ico` and `/img/favicon/site.webmanifest` 200; `bun scripts/deploy.ts check https://<team>.<domain>` from the checkout: every line `ok` (no `Server` but `cloudflare` behind the tunnel, no `X-Powered-By`, `Via` or version); `ss -tlnp` shows only sshd, ports 80 and 443 (none with the tunnel) and 127.0.0.53/54; isolation check all `blocked`, hub lines `200`; both checks in `admin.md` "What a bot can reach" (from a sandbox and from a daemon): public 200, the rest `blocked`; `hub/admins.json` lists the first admin and the hub log has `Admins seeded from HUB_ADMIN_EMAILS` and no `Admins file` error |
| 9. Nightly backups | the two unit files written, one run, `bun deploy.ts nightly status` says `Last run: backups/<time>, … ok`, and `systemctl list-timers vinci-backup.timer` lists the timer |

Don't log in as people: the first admin logs in with the password `vinci:user` printed and changes it in their settings, which also deletes `/opt/vinci/admin-password` on a cloud-init install. Finish by telling the human the address and that the first admin opens the admin panel at `https://<team>.<domain>/admin`. Their first tasks there, in this order (`admin.md`, "Global settings and suggested bots"): set Global settings (Models with an API key, then Chat, Tools, Secrets, Sources), create the suggested bots, then add people with the bots each should start with (each gets a password shown once). Whatever the admin set up is what a person gets. An admin who is not a user is sent to `/admin` when opening the team address.

Deeper checks, when asked to verify an install. Only the daemon image has a shell: `docker exec <container> sh` fails on the hub, web, provisioner and cloudflared, so run checks with `docker exec <container> bun -e '…'` (not cloudflared). In `fetch` errors, code `23` is a timeout (packets dropped), `ETIMEOUT` means the name did not resolve, and `FailedToOpenSocket` means no route; all count as blocked.

- **The hub trusts only the API's answer.** From a throwaway container on the `vinci_edge` network, requests to `http://hub:47192/rpc`, `/`, `/admin`, `/admin/api/me`, `/hub/pair`, `/admin/api/users/x/rpc/conversation/list`, `/admin/api/users/x/files/x/y`, `/admin/api/audit`, `/admin/activity` and `/hub/whoami` with a made-up `vinci_session` cookie, or with identity headers (`x-vinci-email`, `cf-access-authenticated-user-email`), must get 401, as must no cookie; `/favicon.ico` 200; `/img/favicon/` 401. Only status codes are printed:

  ```sh
  cd /opt/vinci && docker run --rm --name vinci-session-probe --network vinci_edge -e EMAIL=<a user email> --entrypoint bun "$(sed -n 's/^VINCI_REGISTRY=//p' .env)vinci-hub:$(sed -n 's/^VINCI_TAG=//p' .env)" -e 'for(const p of ["/rpc","/","/admin","/admin/api/me","/hub/pair","/admin/api/users/x/rpc/conversation/list","/admin/api/users/x/files/x/y","/admin/api/audit","/admin/activity","/hub/whoami"])for(const h of [{},{cookie:"vinci_session=1|made0up"},{"x-vinci-email":process.env.EMAIL,"cf-access-authenticated-user-email":process.env.EMAIL}]){const r=await fetch("http://hub:47192"+p,{headers:h,redirect:"manual"});console.log(p,Object.keys(h)[0]??"none",r.status)}'
  ```
- **Hardening.** `docker inspect` each container: `ReadonlyRootfs` true, `CapDrop [ALL]`, `no-new-privileges`, no `PortBindings`, daemons `User 1000:1000` with memory, CPU and PID limits; each daemon's only network is its `vinci_user-<id>`; its ipc mount has `Subpath <id>`; no Docker socket inside. Only the provisioner has the socket: `User 0:0`, no `CapAdd`, network `vinci_provisioner` only (hub and provisioner, internal). The firewall is the only container on the host network and the only one with capabilities: `User 0:0`, `CapAdd [NET_ADMIN]`, no socket, no mounts.
- **Bot sandbox.** Each `vinci-sandbox-<id>-1`: `ReadonlyRootfs` true, `CapDrop [ALL]`, `no-new-privileges`, `User 1000:1000`, memory, CPU and PID limits, its only network `vinci_sandbox-<id>` (bridge `mv-d…`, nothing else on it), mounts only `disk-<id>` subpaths `agents` and `bot-home` (at `/home/bot`, read-write; an ext4 loop mount of `disks/<id>.img` with `nosuid,nodev`), `data-<id>` subpath `home/.agents` (read only) and `vinci_sandbox-<id>` at `/run/sandbox` (read only); in the person's daemon `/data/bot-home` is an empty read-only tmpfs. `find / -xdev -perm /6000 -type f` in the sandbox prints nothing. On a throwaway person with a Full bot (mock model, as below), a bot's `env` shows no model key, `ls /data/data /data/pi` fails, `ls /run/sandbox` lists `exec.sock` (and `proxy.sock`, `ca-bundle.pem` once a secret exists) and `rm /run/sandbox/exec.sock` says `Read-only file system`, and `pip install --user cowsay && cowsay -t hi` works and still works after `docker compose restart sandbox-<id>`. `bun deploy.ts status` prints every daemon and sandbox `running (healthy)`. `docker compose stop sandbox-<id>` makes that bot's next tool call answer *Bot tools are off* after about 10 s; `bun deploy.ts apply` starts it again. With a command MCP server on that bot (`bun` with a small script in `~/.agents`), its process shows in `docker compose exec sandbox-<id>` (`/proc/*/cmdline`) and not in `daemon-<id>`.
- **Disk limits.** `bun deploy.ts status` lists every person and the template with `disk … of <SANDBOX_DISK less about 3%>` and the server's free space, and exits 0; `findmnt | grep disks/` shows one `loop` mount per person with `nosuid,nodev,discard`; `systemctl is-enabled vinci-disks.service` says `enabled`; `docker inspect -f '{{.HostConfig.LogConfig.Config}}'` on any container shows `max-size:10m max-file:3`.
- **The provisioner is reachable only from the hub.** From each daemon and from the web container, `fetch` to `http://provisioner:47193/health` and to the provisioner's IP on both its networks must fail; from the hub, `http://provisioner:47193/health` answers 401 without the token. Linux only (OrbStack lets a daemon reach other bridges).

  ```sh
  cd /opt/vinci && P1=$(docker inspect vinci-provisioner-1 -f '{{(index .NetworkSettings.Networks "vinci_provisioner").IPAddress}}') && for c in $(docker compose ps --format '{{.Name}}' | grep -E 'daemon-|web|hub'); do for u in provisioner $P1; do printf '%s -> %s: ' $c $u; docker exec $c bun -e "fetch('http://$u:47193/health',{signal:AbortSignal.timeout(3000)}).then(r=>console.log('REACHED',r.status),e=>console.log('blocked',e.code||e.name))"; done; done
  ```

  Expected: every daemon and web line `blocked`; the hub `REACHED 401` for both.
- **The provisioner works without the panel.** Don't log in as the admin; prove

## Add a person

Normally the admin panel does this, and shows the person's password once. By hand: `admin.md`, "Add a person": add the line, `bun deploy.ts apply` on the server, then `docker compose exec -T api php artisan vinci:user <email>` (the password is in the output, once: never repeat it). Proof: `vinci-daemon-<id>-1` healthy; `grep -c '"id"' /opt/vinci/hub/users.json` equals the number of enabled people (`daemonUrl` also counts the template). The hub's `Users loaded` log line only updates on the next request, so don't wait for it. Nobody else's container or the hub restarts.

Bots for a person are created in the admin panel (or by the person in the app). Without the panel, `admin.md`, "Create a bot for someone", uses the person's owner socket. Never pair a device into their Vinci.

## Global settings and suggested bots

Done in the panel by an admin (`admin.md`, "Global settings and suggested bots"); you don't log in as the admin, so you only check the server side. The template workspace (`vinci-daemon-template-1`, volume `vinci_data-template`) is kept by every `apply`; never add `template` to `users.yaml` (refused) and never pair a device into it. Proof after the admin's changes: `hub/global.json` exists, and a sync status of everyone `in-sync` (the admin reads *Sync status* in the panel). After editing files in the template's `~/.agents` by hand, the admin runs *Sync now*: editing files triggers no copy. Back it up like a person (`bun deploy.ts backup template`); it can't be purged. It costs one more daemon's memory.

## Disable a person

`admin.md`, "Disable a person": `enabled: false` in the long form, then `apply`; the hub refuses their login with *Your sign-in is turned off*. Proof: no `vinci-daemon-<id>-1`, `vinci_data-<id>` still there, their email gone from `hub/users.json`.

## Remove a person

`admin.md`, "Remove a person": delete the line, then `apply` (removing them in the panel also deletes their login account and its logins). Proof: their container and `vinci_user-<id>` network are gone, `users.json` count dropped. ## Upgrade and roll back

`admin.md`, "Upgrades": "The normal upgrade", then "Check after an upgrade", after reading "Notes for older versions" for every version the install passes. The first upgrade to a version with the provisioner and admin panel also needs `admins:` in `users.yaml`, `HUB_ADMIN_EMAILS` and `PROVISIONER_TOKEN` in `.env`, and one `bun deploy.ts apply` afterwards (proof: `stat -c '%u:%g %a' /opt/vinci/hub` prints `1000:0 770`). Order: pull the new release tag (`ghcr.io/meetvinci`, no login; moving off the old registry also sets `VINCI_REGISTRY=ghcr.io/meetvinci/` in `.env`; build and load only a commit CI has not built, with `VINCI_REGISTRY=` empty), copy the deployment files again from a checkout of that tag (never `.env`), back up everyone with `bun deploy.ts nightly` (every person, the template and the hub folder with the audit trail; `nightly status` must say `ok`) and note that run's time (retention keeps every run of the last 7 days with one, so a later run that day no longer deletes it), then on the first upgrade to the firewall version check `iptables --version` says `(nf_tables)` (stop and report if not; never run `iptables-legacy`, gotcha 144) and arm the undo timer from `admin.md` (`systemd-run --on-active=10m --unit=vinci-fw-undo --working-directory=/opt/vinci /usr/local/bin/bun deploy.ts firewall remove`; it starts the firewall in the next step, `up -d`, not in `apply`), set `VINCI_TAG`, `docker compose up -d --wait`, then `bun deploy.ts apply` (on the first upgrade to the firewall version it removes and recreates the hub and every daemon on the new networks itself, gotchas 142 and 177; a `deploy.ts` from before that needed a manual `docker compose rm -sf …` first; when the new `deploy.ts` changes the daemons' settings, as the upgrade to the firewall wait did, it recreates every daemon once more, gotcha 190) (always: it renders what the new `deploy.ts` adds; the upgrade to global settings otherwise runs no template and the hub logs `template: false`). Proof: `docker compose ps` shows the new tag on hub, provisioner, web, `vinci-daemon-template-1` and every daemon, all healthy, and `bun deploy.ts firewall status` `healthy`; with the undo timer armed, a fresh SSH login, `iptables -S INPUT` as before plus only the `VINCI-DAEMONS-HOST` jump, the hub reaching every daemon and a chat on a throwaway person come before `systemctl stop vinci-fw-undo.timer`; the hub's `Users loaded` line says `template: true` after the next request; `/rpc` still 302 from outside; from the audit trail version on, `hub/audit.sqlite` exists as `1000 1000` mode 600 (the hub creates it). The new hub may log `The provisioner did not take the admin list yet; trying again` once (`Can't reach your server`, the provisioner is being recreated too): harmless when no error follows; one or two `502` `Request refused` for `/health` (`The daemon of <id> did not answer`) during the restart are a person's open tab and harmless too. From wave 6 on, every daemon and the template has `DAEMON_TEAM=true` (`docker inspect … .Config.Env`; from one-mode piece H on every daemon refuses by itself and ignores it, and `daemon.yaml` keeps it for one release only so an older image under the new files still refuses, gotcha 314) and on the first upgrade to it nobody is advanced (`grep -c advanced users.yaml hub/users.json`: `0`); later upgrades keep whoever the admin switched on. Nothing to press afterwards: every hub start copies every global section again, as **Sync now** does (gotcha 170); proof a minute after `up -d --wait`: `docker compose logs hub` has `Admin made a change` with `by: hub start` and `action: global/sync`, and `GET /admin/api/global/status` (side hub) has no *failed* section. Snapshot every person before and after over their owner sockets (settings, bots, devices; no conversation reads) to show their data is intact. The upgrade to global settings changes nobody's values: existing people have no record in `hub/global.json` and stay *overridden* in every section; never switch a section of theirs to global without the human's yes (it replaces their secrets, `~/.agents` or stored keys). Roll back with the old version's deployment files, the old tag, `docker compose up -d --wait` and `bun deploy.ts apply` (past the bot sandbox: `apply` first, and check bot folders for plugins and `mcp.json` files bots wrote, gotcha 219): the wave 1 hub refuses a `users.json` with a `template` key and lets nobody in until the old `apply` rewrites it. Before rolling back past wave 6 (the Advanced switch), `cp users.yaml users.yaml.before-rollback`: that version's hub and provisioner drop `advanced` from `users.yaml` at start (gotcha 171); after upgrading again, add `advanced: true` back under each person who has it in the copy and run `bun deploy.ts apply`. A rollback to wave 6 or later keeps it. Restore backups only if the new version changed data; a rollback past a daemon database migration (`0006_bot_start`, copied bots start on first open) always does: restore every person and `template` from the pre-upgrade backup, or the old daemons restart in a loop (gotcha 199). The first upgrade to the version with the bot sandbox needs the `vinci-sandbox` image and `sandbox.yaml` and nothing else; between `up -d --wait` and `apply` every daemon restarts in a loop (`… no volume is mounted there`, or `EROFS … /run/sandbox/exec.sock` from an image before gotcha 295: the old per-person file has no shared folder) and `up` exits 1 with `container vinci-daemon-<id>-1 is unhealthy`; that is expected, go on with `apply`, which creates every sandbox and disk and recreates everyone (proof: `bun deploy.ts status` exits 0; gotcha 280). Remove old image tags by name once the human is happy.

## Back up and restore

`admin.md`, "Backups". `bun deploy.ts nightly install` once (a systemd timer, `BACKUP_TIME` in `.env`); `bun deploy.ts nightly` backs up everyone, the template, the hub folder and the deployment files into `backups/<time>/` with a `manifest.json`, one person stopped at a time; `nightly status` shows the last run and exits non-zero when it failed or is older than 36 h. Retention (every run of the 7 newest days with one, the newest of 4 weeks) runs only after a good run. The off-site copy is off until the human sets `BACKUP_S3_BUCKET`, the other `BACKUP_S3_` settings and `BACKUP_PASSPHRASE` in `.env` (any S3-compatible bucket: S3, R2, B2); each run then encrypts every kept run the bucket lacks with GnuPG and uploads `<prefix><time>.tar.gpg` and `<time>.sha256`, applies the same retention in the bucket (only to names like those), and records the last upload and failure in `backups/offsite.json`, which `nightly status` shows (non-zero exit while the last upload failed). A failed upload keeps the local backup and is retried by the next run. Never print or ask for the passphrase in a transcript; the human keeps it in a password manager. On a lost server, `bun deploy.ts nightly fetch` lists and `nightly fetch <time>` downloads, checks and decrypts a run into `backups/<time>/` with only `deploy.ts`, the images and a `.env` of `VINCI_TAG`, `VINCI_REGISTRY`, the `BACKUP_S3_` lines and the passphrase (`admin.md`, "Restore from the off-site copy"). `bun deploy.ts backup <id>` still backs up one person. Restore one person with `bun deploy.ts restore <id> backups/<time>` (or a file), which checks the checksum and first saves the current data; a whole install on a fresh server with `restore backups/<time>` after unpacking its `deployment.tar.gz` (refused when `hub/` is not empty). Backups hold every key: never print them or copy them anywhere the human did not choose. Proof: `nightly status` `ok`, files mode 600; `systemctl list-timers vinci-backup.timer` lists the next run, and `systemctl start vinci-backup.service` runs the timer's job once by hand (it blocks until done; `journalctl -u vinci-backup.service` then has one `Backed up` line per workspace and the retention's `Deleted` lines); after a restore, `Restored <id>` and the container healthy. A run made by hand stays like a nightly one, also when another run follows on the same UTC day.
