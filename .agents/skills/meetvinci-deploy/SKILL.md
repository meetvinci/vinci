# Deploy a team install

The human guides in `docs/team-workspace/` are the single source of truth for commands. This skill says what to ask, in what order to work, what never to do, and how to prove each step. Read the guide section named in each step and run its commands as written; when a command fails or its output differs, use the "If it differs" notes there and `troubleshooting.md` before improvising. When you fix a guide's command, fix the guide too.

## Ask first

Ask the human for everything below before touching anything, in one message. Don't guess any of it.

| What | Example | Used for |
| --- | --- | --- |
| Server address and how to reach it | `root@203.0.113.10`, key file or SSH options | every server step |
| Cloudflare zone, team hostname, object name | `example.com`, `acme.example.com`, `meetvinci-acme` | Cloudflare steps; the name must start with `meetvinci-` |
| Where the Cloudflare API token is | `op://<vault>/<item>/credential` | read inside each command that needs it |
| People: id and email each | `alice: alice@example.com` | `users.yaml` |
| First admin of the admin panel (need not be one of the people; admins are fully trusted) | `admin@example.com` | `admins:` in `users.yaml`, `HUB_ADMIN_EMAILS` (the same email in both) |
| How Cloudflare lets people in: a domain rule for the company's email domain (recommended when everyone has one; never a public mail domain), or a list of emails plus a small server token so the panel keeps it in step; by hand only as a fallback | `--domain example.com`, or a token at `op://…` | install steps 5 and 6 |
| Model keys: provider and where they are, or none. Keys can also be set once in the panel's Global settings → Models, which copies them to everyone | `ANTHROPIC_API_KEY` from `op://…` | `.env` or Global settings |
| Optional: SSH through the tunnel, admin emails | `acme-ssh.example.com` | `--ssh-hostname`, `--ssh-email` |
| For a change: the image tag in use | `MEETVINCI_TAG` in `/opt/meetvinci/.env` | upgrades and teardown |

If the token read fails (1Password prints `authorization timeout`, the script says `CLOUDFLARE_API_TOKEN is unset or empty`), ask the human to unlock their password manager. Never ask them to paste the token or a login code.

## Safety rules

- **Never print secrets.** Not the API token, `TUNNEL_TOKEN`, `PROVISIONER_TOKEN`, model keys, `/opt/meetvinci/.env`, `auth.json`, `models.json` with keys, or backups. Read tokens inside the command that uses them (`CLOUDFLARE_API_TOKEN="$(op read '…')" bun …`); never export them in a shell profile, write them to a file, or put them on the server. The only Cloudflare secrets the server holds are `TUNNEL_TOKEN` and, only if the human asks for Access sync, a separate narrow `CLOUDFLARE_API_TOKEN`, both in `/opt/meetvinci/.env` (mode 600). Never put the install token on the server. Hide emails in anything you post publicly.
- **Protect before DNS.** Only `bun scripts/deploy.ts cloudflare apply` creates Cloudflare objects; it creates Access before the DNS record. Never create the DNS record, tunnel routes or Access apps by hand or in the dashboard.
- **Exact-name ownership on Cloudflare.** Every object is `meetvinci-<team>` or `meetvinci-<team>-<suffix>`; DNS records carry the comment `meetvinci deploy meetvinci-<team>`. Accounts hold unrelated objects with similar names (other tunnels, Access apps, `meetvinci-…` apps on other hostnames): never change or delete anything by prefix or by hand. Before `cloudflare destroy --yes`, run it without `--yes`, read every listed line, and check each names `meetvinci-<team>` or `<team>.<domain>` exactly.
- **Never clean Docker host-wide.** No `docker system prune`, `docker volume prune`, `docker image prune`, `docker network prune` or `docker builder prune`. Remove only objects you created, by name: `meetvinci-daemon:<tag>` images, `meetvinci_data-<id>` volumes after a confirmed purge, containers you started for tests.
- **Data deletion needs the human's yes.** `bun deploy.ts purge <id>`, `docker volume rm`, deleting backups, `rm -rf /opt/meetvinci` and `cloudflare destroy --yes` are irreversible: list what goes and wait for confirmation.
- **Never touch the firewall's chains or the host's `INPUT` policy by hand.** The `firewall` service owns `MEETVINCI-DAEMONS` and `MEETVINCI-DAEMONS-HOST`, puts them back within 2 s and then reports unhealthy for one check (`bun deploy.ts firewall status`); open an internal destination only through `MEETVINCI_INTERNAL_ALLOW` in `.env` and only when the human names it.
- **Linux only.** Isolation between people is Docker Engine's per-network rule. Never run a team on OrbStack or Docker Desktop, and prove isolation on the real server.
- **Build images off the server**, on the admin's computer (`bun run build:images`), and load them over SSH.
- **Don't attach anything to `meetvinci_user-<id>`, `meetvinci_sandbox-<id>` or `meetvinci_provisioner` networks**, and don't pair your own device into a person's MeetVinci: a device paired there can act as that person. The provisioner holds the Docker socket: never publish its port, give it capabilities, or let anything but the hub reach it.

## Install

Follow `docs/team-workspace/install.md` steps 1 to 8 in order. Stop at the first failed check and report it.

| Step | Proof it worked |
| --- | --- |
| 1. Check the server | `x86_64`, Ubuntu 24.04, `avx2`, at least 3.7 GiB memory, 40 GB free |
| 2. Docker | server version 26 or newer, `docker compose version` works, service `enabled` |
| 3. Images and files | `amd64` for all six images locally; six `Loaded image:` lines; `/opt/meetvinci` mode 700 with the five files; `.env` mode 600; `bun --version` on the server |
| 4. `users.yaml` | one `<id>: <email>` per person under `users:`; the first admin under `admins:` |
| 5. Cloudflare | `created` or `unchanged` for the tunnel, policies, apps, routes and DNS; the six values printed (`MEETVINCI_PUBLIC_HOST`, `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `CLOUDFLARE_ZONE`, `CLOUDFLARE_NAME`, `CLOUDFLARE_ACCESS_DOMAINS`, empty without `--domain`); `cloudflare.env` written (git ignores it). Ask the human first: a domain rule (`--domain`) or a list of emails plus the small server token (install step 6); never a public mail domain |
| 6. Tunnel token | `600 root` and `6` from the step's check; local `cloudflare.env` deleted |
| 7. Start | `HUB_ADMIN_EMAILS` set and `1` from the `PROVISIONER_TOKEN` check; `Applied <n> users: … (and the template workspace)`; every container `(healthy)`, the provisioner, `meetvinci-daemon-template-1` and every `meetvinci-sandbox-<id>-1` included, `bun deploy.ts status` exits 0, and `bun deploy.ts firewall status` says `healthy`; `Registered tunnel connection` in the cloudflared log; the provisioner's `listening` line says `Access sync on` when step 6 put a token on the server (`; domain rule @<domain>` with a domain rule) |
| 8. Check | `/rpc` and `/admin` 302 to `<team>.cloudflareaccess.com`, `/favicon.ico` and `/img/favicon/site.webmanifest` 200; `ss -tlnp` shows only sshd and 127.0.0.53/54; isolation check all `blocked`, hub lines `200`; both checks in `admin.md` "What a bot can reach" (from a sandbox and from a daemon): public 200, the rest `blocked`; `hub/admins.json` lists the first admin and the hub log has `Admins seeded from HUB_ADMIN_EMAILS` and no `Admins file` error |

You cannot pass Cloudflare Access yourself: it emails a one-time code to the person. Finish by telling the human the address, which emails can log in, and that the first admin opens the admin panel at `https://<team>.<domain>/admin`. Their first tasks there, in this order (`admin.md`, "Global settings and suggested bots"): set Global settings (Models with an API key, then Chat, Tools, Secrets, Sources), create the suggested bots, then add people with the bots each should start with. Whatever the admin set up is what a person gets. An admin who is not a user is sent to `/admin` when opening the team address.

Deeper checks, when asked to verify an install. Only the daemon image has a shell: `docker exec <container> sh` fails on the hub, web, provisioner and cloudflared, so run checks with `docker exec <container> bun -e '…'` (not cloudflared). In `fetch` errors, code `23` is a timeout (packets dropped), `ETIMEOUT` means the name did not resolve, and `FailedToOpenSocket` means no route; all count as blocked.

- **The hub trusts only Cloudflare.** From a throwaway container on the `meetvinci_tunnel` network, requests to `http://hub:47192/rpc`, `/`, `/admin`, `/admin/api/me`, `/hub/pair` and the viewer's `/admin/api/users/x/rpc/conversation/list` and `/admin/api/users/x/files/x/y`, the audit trail's `/admin/api/audit`, the **Activity** page `/admin/activity` and the person's `/hub/whoami` with a self-made JWT (any algorithm, any key, the real `ACCESS_AUD` and a real email) must get 401, as must no JWT; `/favicon.ico` 200; `/img/favicon/` 401. A quick forged token (HS256), with nothing printed but status codes. It reads only the three values it needs from `.env`; never source the whole file into your shell (risk 52 in the reference):

  ```sh
  cd /opt/meetvinci && get() { sed -n "s/^$1=//p" .env; } && docker run --rm --name meetvinci-jwt-probe --network meetvinci_tunnel -e AUD="$(get ACCESS_AUD)" -e ISS="$(get ACCESS_TEAM_DOMAIN)" -e EMAIL=<a user email> --entrypoint bun "meetvinci-hub:$(get MEETVINCI_TAG)" -e 'const b=(s)=>Buffer.from(s).toString("base64url");const t=Math.floor(Date.now()/1000);const h=b(JSON.stringify({alg:"HS256",typ:"JWT"}))+"."+b(JSON.stringify({aud:[process.env.AUD],iss:process.env.ISS,email:process.env.EMAIL,iat:t,exp:t+600}));const k=await crypto.subtle.importKey("raw",new TextEncoder().encode("x"),{name:"HMAC",hash:"SHA-256"},false,["sign"]);const j=h+"."+Buffer.from(await crypto.subtle.sign("HMAC",k,new TextEncoder().encode(h))).toString("base64url");for(const p of ["/rpc","/","/admin","/admin/api/me","/hub/pair","/admin/api/users/x/rpc/conversation/list","/admin/api/users/x/files/x/y","/admin/api/audit","/admin/activity","/hub/whoami"])for(const x of [null,j]){const r=await fetch("http://hub:47192"+p,{headers:x?{"cf-access-jwt-assertion":x}:{},redirect:"manual"});console.log(p,x?"forged":"none",r.status)}'
  ```
- **Hardening.** `docker inspect` each container: `ReadonlyRootfs` true, `CapDrop [ALL]`, `no-new-privileges`, no `PortBindings`, daemons `User 1000:1000` with memory, CPU and PID limits; each daemon's only network is its `meetvinci_user-<id>`; its ipc mount has `Subpath <id>`; no Docker socket inside. Only the provisioner has the socket: `User 0:0`, no `CapAdd`, networks `meetvinci_provisioner` (hub and provisioner only, internal) and `meetvinci_egress` (provisioner only). The firewall is the only container on the host network and the only one with capabilities: `User 0:0`, `CapAdd [NET_ADMIN]`, no socket, no mounts.
- **Bot sandbox.** Each `meetvinci-sandbox-<id>-1`: `ReadonlyRootfs` true, `CapDrop [ALL]`, `no-new-privileges`, `User 1000:1000`, memory, CPU and PID limits, its only network `meetvinci_sandbox-<id>` (bridge `mv-d…`, nothing else on it), mounts only `disk-<id>` subpaths `agents` and `bot-home` (at `/home/bot`, read-write; an ext4 loop mount of `disks/<id>.img` with `nosuid,nodev`), `data-<id>` subpath `home/.agents` (read only) and `meetvinci_sandbox-<id>` at `/run/sandbox` (read only); in the person's daemon `/data/bot-home` is an empty read-only tmpfs. `find / -xdev -perm /6000 -type f` in the sandbox prints nothing. On a throwaway person with a Full bot (mock model, as below), a bot's `env` shows no model key, `ls /data/data /data/pi` fails, `ls /run/sandbox` lists `exec.sock` (and `proxy.sock`, `ca-bundle.pem` once a secret exists) and `rm /run/sandbox/exec.sock` says `Read-only file system`, and `pip install --user cowsay && cowsay -t hi` works and still works after `docker compose restart sandbox-<id>`. `bun deploy.ts status` prints every daemon and sandbox `running (healthy)`. `docker compose stop sandbox-<id>` makes that bot's next tool call answer *Bot tools are off* after about 10 s; `bun deploy.ts apply` starts it again. With a command MCP server on that bot (`bun` with a small script in `~/.agents`), its process shows in `docker compose exec sandbox-<id>` (`/proc/*/cmdline`) and not in `daemon-<id>`.
- **Disk limits.** `bun deploy.ts status` lists every person and the template with `disk … of <SANDBOX_DISK less about 3%>` and the server's free space, and exits 0; `findmnt | grep disks/` shows one `loop` mount per person with `nosuid,nodev,discard`; `systemctl is-enabled meetvinci-disks.service` says `enabled`; `docker inspect -f '{{.HostConfig.LogConfig.Config}}'` on any container shows `max-size:10m max-file:3`.
- **The provisioner is reachable only from the hub.** From each daemon and from the web container, `fetch` to `http://provisioner:47193/health` and to the provisioner's IP on both its networks must fail; from the hub, `http://provisioner:47193/health` answers 401 without the token. Linux only (OrbStack lets a daemon reach other bridges).

  ```sh
  cd /opt/meetvinci && P1=$(docker inspect meetvinci-provisioner-1 -f '{{(index .NetworkSettings.Networks "meetvinci_provisioner").IPAddress}}') && P2=$(docker inspect meetvinci-provisioner-1 -f '{{(index .NetworkSettings.Networks "meetvinci_egress").IPAddress}}') && for c in $(docker compose ps --format '{{.Name}}' | grep -E 'daemon-|web|hub'); do for u in provisioner $P1 $P2; do printf '%s -> %s: ' $c $u; docker exec $c bun -e "fetch('http://$u:47193/health',{signal:AbortSignal.timeout(3000)}).then(r=>console.log('REACHED',r.status),e=>console.log('blocked',e.code||e.name))"; done; done
  ```

## Add a person

Normally the admin panel does this. By hand: `admin.md`, "Add a person": add the line, `bun deploy.ts apply` on the server, then `cloudflare emails` from the admin's computer (skip it if the email is inside `CLOUDFLARE_ACCESS_DOMAINS`, or the server has `CLOUDFLARE_API_TOKEN` and the provisioner log says `Access sync on`; run it anyway after a by-hand change; it keeps the domain rule). Proof: `meetvinci-daemon-<id>-1` healthy; `grep -c '"id"' /opt/meetvinci/hub/users.json` equals the number of enabled people (`daemonUrl` also counts the template); `Access policy meetvinci-<team>-allow: updated`. The hub's `Users loaded` log line only updates on the next request, so don't wait for it. Nobody else's container or the hub restarts.

Bots for a person are created in the admin panel (or by the person in the app). Without the panel, `admin.md`, "Create a bot for someone", uses the person's owner socket. Never pair a device into their MeetVinci.

## Global settings and suggested bots

Done in the panel by an admin (`admin.md`, "Global settings and suggested bots"); you cannot pass Access, so you only check the server side. The template workspace (`meetvinci-daemon-template-1`, volume `meetvinci_data-template`) is kept by every `apply`; never add `template` to `users.yaml` (refused) and never pair a device into it. Proof after the admin's changes: `hub/global.json` exists, and a sync status of everyone `in-sync` (the admin reads *Sync status* in the panel). After editing files in the template's `~/.agents` by hand, the admin runs *Sync now*: editing files triggers no copy. Back it up like a person (`bun deploy.ts backup template`); it can't be purged. It costs one more daemon's memory.

`admin.md`, "Disable a person": `enabled: false` in the long form, `apply`, then `cloudflare emails`. Proof: no `meetvinci-daemon-<id>-1`, `meetvinci_data-<id>` still there, their email gone from `hub/users.json`.

## Upgrade and roll back

`admin.md`, "Upgrades". The first upgrade to a version with the provisioner and admin panel also needs `admins:` in `users.yaml`, `HUB_ADMIN_EMAILS` and `PROVISIONER_TOKEN` in `.env`, and one `bun deploy.ts apply` afterwards (proof: `stat -c '%u:%g %a' /opt/meetvinci/hub` prints `1000:0 770`). Order: build and load the new tag, copy the deployment files again (never `.env`), back up everyone with `bun deploy.ts nightly` (every person, the template and the hub folder with the audit trail; `nightly status` must say `ok`) and note that run's time (retention keeps every run of the last 7 days with one, so a later run that day no longer deletes it), then on the first upgrade to the firewall version check `iptables --version` says `(nf_tables)` (stop and report if not; never run `iptables-legacy`, gotcha 144) and arm the undo timer from `admin.md` (`systemd-run --on-active=10m --unit=meetvinci-fw-undo --working-directory=/opt/meetvinci /usr/local/bin/bun deploy.ts firewall remove`; it starts the firewall in the next step, `up -d`, not in `apply`), set `MEETVINCI_TAG`, `docker compose up -d --wait`, then `bun deploy.ts apply` (on the first upgrade to the firewall version it removes and recreates the hub and every daemon on the new networks itself, gotchas 142 and 177; a `deploy.ts` from before that needed a manual `docker compose rm -sf …` first; when the new `deploy.ts` changes the daemons' settings, as the upgrade to the firewall wait did, it recreates every daemon once more, gotcha 190) (always: it renders what the new `deploy.ts` adds; the upgrade to global settings otherwise runs no template and the hub logs `template: false`). Proof: `docker compose ps` shows the new tag on hub, provisioner, web, `meetvinci-daemon-template-1` and every daemon, all healthy, and `bun deploy.ts firewall status` `healthy`; with the undo timer armed, a fresh SSH login, `iptables -S INPUT` as before plus only the `MEETVINCI-DAEMONS-HOST` jump, the hub reaching every daemon and a chat on a throwaway person come before `systemctl stop meetvinci-fw-undo.timer`; the hub's `Users loaded` line says `template: true` after the next request; `/rpc` still 302 from outside; from the audit trail version on, `hub/audit.sqlite` exists as `1000 1000` mode 600 (the hub creates it). The new hub may log `The provisioner did not take the admin list yet; trying again` once (`Can't reach your server`, the provisioner is being recreated too): harmless when no error follows; one or two `502` `Request refused` for `/health` (`The daemon of <id> did not answer`) during the restart are a person's open tab and harmless too. From wave 6 on, every daemon and the template has `DAEMON_TEAM=true` (`docker inspect … .Config.Env`) and on the first upgrade to it nobody is advanced (`grep -c advanced users.yaml hub/users.json`: `0`); later upgrades keep whoever the admin switched on. Nothing to press afterwards: every hub start copies every global section again, as **Sync now** does (gotcha 170); proof a minute after `up -d --wait`: `docker compose logs hub` has `Admin made a change` with `by: hub start` and `action: global/sync`, and `GET /admin/api/global/status` (side hub) has no *failed* section. Snapshot every person before and after over their owner sockets (settings, bots, devices; no conversation reads) to show their data is intact. The upgrade to global settings changes nobody's values: existing people have no record in `hub/global.json` and stay *overridden* in every section; never switch a section of theirs to global without the human's yes (it replaces their secrets, `~/.agents` or stored keys). Roll back with the old version's deployment files, the old tag, `docker compose up -d --wait` and `bun deploy.ts apply` (past the bot sandbox: `apply` first, and check bot folders for plugins and `mcp.json` files bots wrote, gotcha 219): the wave 1 hub refuses a `users.json` with a `template` key and lets nobody in until the old `apply` rewrites it. Before rolling back past wave 6 (the Advanced switch), `cp users.yaml users.yaml.before-rollback`: that version's hub and provisioner drop `advanced` from `users.yaml` at start (gotcha 171); after upgrading again, add `advanced: true` back under each person who has it in the copy and run `bun deploy.ts apply`. A rollback to wave 6 or later keeps it. Restore backups only if the new version changed data; a rollback past a daemon database migration (`0006_bot_start`, copied bots start on first open) always does: restore every person and `template` from the pre-upgrade backup, or the old daemons restart in a loop (gotcha 199). The first upgrade to the version with the bot sandbox needs the `meetvinci-sandbox` image and `sandbox.yaml` and nothing else; between `up -d --wait` and `apply` every daemon restarts in a loop (`EROFS … /run/sandbox/exec.sock`: the old per-person file has no shared folder) and `up` exits 1 with `container meetvinci-daemon-<id>-1 is unhealthy`; that is expected, go on with `apply`, which creates every sandbox and disk and recreates everyone (proof: `bun deploy.ts status` exits 0; gotcha 280). Remove old image tags by name once the human is happy.

## Back up and restore

`admin.md`, "Backups". `bun deploy.ts nightly install` once (a systemd timer, `BACKUP_TIME` in `.env`); `bun deploy.ts nightly` backs up everyone, the template, the hub folder and the deployment files into `backups/<time>/` with a `manifest.json`, one person stopped at a time; `nightly status` shows the last run and exits non-zero when it failed or is older than 36 h. Retention (every run of the 7 newest days with one, the newest of 4 weeks) runs only after a good run. The off-site copy is off until the human sets `BACKUP_S3_BUCKET`, the other `BACKUP_S3_` settings and `BACKUP_PASSPHRASE` in `.env` (any S3-compatible bucket: S3, R2, B2); each run then encrypts every kept run the bucket lacks with GnuPG and uploads `<prefix><time>.tar.gpg` and `<time>.sha256`, applies the same retention in the bucket (only to names like those), and records the last upload and failure in `backups/offsite.json`, which `nightly status` shows (non-zero exit while the last upload failed). A failed upload keeps the local backup and is retried by the next run. Never print or ask for the passphrase in a transcript; the human keeps it in a password manager. On a lost server, `bun deploy.ts nightly fetch` lists and `nightly fetch <time>` downloads, checks and decrypts a run into `backups/<time>/` with only `deploy.ts`, the images and a `.env` of `MEETVINCI_TAG`, the `BACKUP_S3_` lines and the passphrase (`admin.md`, "Restore from the off-site copy"). `bun deploy.ts backup <id>` still backs up one person. Restore one person with `bun deploy.ts restore <id> backups/<time>` (or a file), which checks the checksum and first saves the current data; a whole install on a fresh server with `restore backups/<time>` after unpacking its `deployment.tar.gz` (refused when `hub/` is not empty). Backups hold every key: never print them or copy them anywhere the human did not choose. Proof: `nightly status` `ok`, files mode 600; `systemctl list-timers meetvinci-backup.timer` lists the next run, and `systemctl start meetvinci-backup.service` runs the timer's job once by hand (it blocks until done; `journalctl -u meetvinci-backup.service` then has one `Backed up` line per workspace and the retention's `Deleted` lines); after a restore, `Restored <id>` and the container healthy. A run made by hand stays like a nightly one, also when another run follows on the same UTC day.
