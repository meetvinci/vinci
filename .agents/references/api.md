# Orbs backend reference

Only behavior the code does not make obvious. RPC names and inputs: `packages/contracts/src/rpc/rpc.router.ts`. Services: `packages/server/src/services/<domain>/` (product) and `packages/runtime/src/services/<domain>/` (Pi).

## Daemon and storage

```text
DATA_DIR/                     default ~/.config/orbs/
  agents/<botId>/             bot working folder, uploads in .attachments/ (not a sandbox)
  data/app.sqlite             app database
  data/credentials.key        key for the encrypted credentials table
  data/avatars/               uploaded bot avatar images (`<id>.webp`) and each bot's rendered `bots/<botId>.png`, served at `/avatars/*`
  data/daemon.lock            one lock for every store
  data/ipc/rpc.sock           owner-only socket (the private door): `orbs pair` and admin settings
  data/bots/<botId>/runtime.sql   that bot's Pi store; the file is the unit of erasure
  data/bots/<botId>/mcp.json      MCP servers the owner or the bot added for that bot only
  data/bots/<botId>/telemetry.sql model and tool spans, kept 14 days; reset with the store, not backed up
```

- Startup opens and migrates SQL, restores every bot, then resumes Pi. A failing store closes only its bot.
- Backup runs offline with `VACUUM INTO` (`server/src/services/backup/`). A bundle includes the encryption key: treat it as a secret.

## Connection

- Clients probe every address from `server.info()` and use the first, in list order, whose `/health` reports the paired server ID (`server/src/services/server/`). The web server's probes of cookie addresses never follow redirects; native clients' probes do.
- `DAEMON_PUBLIC_URLS` replaces the detected loopback, LAN and Tailscale addresses with those origins (kind `public`); owner-added custom addresses still follow. Public origins are allowed browser Origins and CORS origins. A daemon with public origins issues no first-device grant at startup and prints no PIN; it logs how to run `orbs pair` instead (a team hub pairs browsers over the owner socket). This holds for a single-owner daemon behind its own proxy with `DAEMON_PUBLIC_URLS` too: its owner pairs the first device with `orbs pair`.
- Every call sends `x-bots-protocol`; `serverId` pins a client to one daemon. Mismatches return `PROTOCOL_MISMATCH` or `SERVER_MISMATCH` and are never retried.
- Pairing uses a six-digit PIN that lives five minutes; the QR code and link are Base64 of `{ serverId, addresses, pin }` (`authPairEntry` in `contracts/src/types/auth.types.ts`). Redeem returns the server ID and addresses, so a bare PIN works against a known address. Every wrong PIN counts against all live grants, which die after five misses. Public transport can never bootstrap; only the owner socket can.
- The web proxy only forwards to an address that reports the paired server ID, so a forged cookie cannot redirect it.
- Hub mode (`WEB_HUB_URL`): the hub routes daemon paths by the Access identity, so the web server answers 404 for `/rpc`, `/health`, `/files`, `/avatars` and `/mcp/callback` and never reads cookie addresses. It also answers 404 to those paths for any request carrying `Cf-Access-Jwt-Assertion`, so a hub in front of a web server without `WEB_HUB_URL` fails closed. SSR sends RPC to the hub with the request's `Cf-Access-Jwt-Assertion` header, or its `CF_Authorization` cookie. The browser keeps same-origin `/rpc`.
- The admin panel (`/admin`, team installs) renders only in the browser and never reads the pairing cookie. It calls the hub's `/admin/api/*` and sends a user's RPC over HTTP to `/admin/api/users/<id>/rpc`, which the hub relays to that daemon's owner socket. It keeps its own query client, and its query keys start with `admin-user:<id>`. Global settings and suggested bots are the same screens pointed at the reserved id `template` (`/admin/users/template/*`); a person's sections that follow global are shown read-only, and the hub's 409 `SECTION_FOLLOWS_GLOBAL` on a relay write becomes a message, not a lost connection.
- A hub hands a code it issued to `/connect?code=<pairing payload>` (`connectionSearch`); the page drops it from the URL. A link code (`?code=` or `#code=`) is redeemed at once with the default device name only when every address in it is the page's own origin, or in the desktop shell; any other code is only prefilled for the user to confirm, so a crafted link cannot pair a browser to a foreign server.
- A redirect answering the web client's `/health` check means a login gate's session expired: the page reloads at most once a minute so the gate can sign the user in; unsent drafts live in `localStorage`. The PWA manifest and its icons stay under `/img/favicon/` (plus `/favicon.ico`) so a gate can exempt them.
- Web sends every chat route to `/onboarding/$step` until `onboarding.complete()` stores `onboarding.completedAt` in settings. It is stored per daemon, so devices paired later skip it. A team hub completes it before its first grant, so a provisioned person never sees the onboarding steps.
- The connect page redeems one code once: a link both fills the PIN (which fires the PIN field's completion) and submits itself, and a second redeem of a used PIN fails as `UNAUTHORIZED` and counts as a wrong PIN against every live grant.

## Owner socket (private door)

`data/ipc/rpc.sock` (0600 in a 0700 folder) serves the oRPC router over HTTP `POST /rpc/*` with the same request and response shapes as the public door, to the owner without a device. It exists so an admin (through the hub) and `orbs pair` can manage a daemon without pairing as a device.

- Only the procedures in `RPC_LOCAL_ALLOWLIST` (`server/src/rpc/rpc-local.utils.ts`) are served; every other procedure, including any added later, answers `FORBIDDEN` (403) before throttles or handlers run. A request with an `Origin` header is a 403, anything that is not `POST /rpc/*` (WebSocket upgrades included) a 404. Bodies are capped at the avatar size plus 1 MiB (9 MiB), for `avatars.upload`.
- Served: server info and addresses, onboarding, daemon chat and notification settings, providers and models, plugins, instructions, skills, MCP and MCP OAuth, tool settings, secrets, credentials, bots (list, get, catalog, create, update, delete, model swap), avatar upload, `commands.execute` only for `reset` without handoff text, each bot's routine and todo lists (read only), devices (list, revoke) and `pairing.bootstrap`.
- Refused: every conversation read and write except the daemon-wide chat settings (submit, edit, stop, clear, answers, reactions, read marks, history, watches), tool approvals and pending lists, `compact`, `retry`, `cancel` and handoff resets, creating, changing, running or deleting routines and todos (they belong to the user), `pairing.create` and `pairing.redeem`, attachments, artifacts, activity, notification presence and push, limits, sidebar sections, link previews and bot usage.
- Owner socket only (`localRouter`, `FORBIDDEN` on the public door even with a device), for the team hub's global settings and bot copies, and refused by the hub's admin relay: `providers.export` (API keys stored in Pi's auth store, with their env values; never OAuth logins, env or `models.json` keys) and `providers.import` (makes the stored API keys exactly that list through Pi's own API-key login, answering its prompts with the key then the env values in order; signs out every other stored API key; OAuth logins stay), `secrets.export` (every secret rule with its value), `tools.export` (the Jev key or `null`), `workspace.export` and `workspace.import` (every regular file of `~/.agents`, base64, at most 2000 files and 6 MiB; import writes a sibling folder and swaps it in, so it replaces the folder, and puts the old folder back if the swap fails; symlinked files and folders, `node_modules` and `.git` are skipped, never followed), `bots.exportFiles` and `bots.importFiles` (a bot's instruction files at the top of `agents/<botId>/`, its `.pi/` and `.agents/` folders, and its own `data/bots/<botId>/mcp.json` with the header values derived for it, renamed to the new bot's id on import; import refuses any other credential key and reconfigures the bot).
- Handlers on the allowlist use `ownerRouter`, where `context.device` is `null` on the socket; everything else uses `authedRouter`, which still requires a device, so a listed procedure on `authedRouter` stays refused. Provider and MCP OAuth logins started on the socket belong to `deviceId: null`: only the socket can see, complete or cancel them, and revoking a device never cancels them.
- The public door is unchanged: every procedure except pairing redeem and bootstrap still needs a device token there.
- No peer-credential check: any process with the daemon's uid can call the socket, a bot's bash included (team-workspace risk 1).
- Stdio MCP servers, plugins and skills stay on the list: configuring a user's bots is what the admin panel is for. They run code inside the user's workspace, so an admin can technically read that user's data; admins are fully trusted, and the panel only offers no way to chat or answer as the user.

## Retries and dedupe

- `conversation.submit` dedupes by `requestId`: a reused ID returns the same submission even with new content. Clients never retry commands or submissions on their own.
- Peer delivery submits with `bots.delivery:<senderStoreId>:<taskId>`, so a rerun after a crash delivers once (`runtime/src/services/collaboration/collaboration-delivery.task.ts`).
- Tools that mutate use `replay: 'unsafe'`: after a crash, read state before retrying.

## Busy modes (`whenBusy`)

`followUp` queues after the reply, `steer` joins after the current tool round, `interrupt` aborts the run and goes first (`CONFLICT` if a newer run started), `reject` fails when busy. When omitted: the chat's mode, then the daemon default, then `followUp`.

## Model fallback

One retry on the bot's `fallbackModel` only when a request fails before any output with an auth, quota or transient provider error (`runtimeModelCanFallback` in `runtime/src/services/runtime/runtime-model-stream.utils.ts`).

## Approvals

Read-only, Ask, Auto and Full. Auto asks Jev and approves only with a safe score of at least 0.9 and an ask-first score of at most 0.1 (`server/src/services/tool/tool.constants.ts`); otherwise it asks the owner. Only exact trusted registrations count as reads. Approval state lives in Pi task documents and survives restart.

## Secrets

`bot_secret` stores values encrypted as `secrets.<NAME>` with allowed hosts. Bash reads `$NAME`. Mode `proxy` (default) keeps a placeholder in the command and swaps in the value only over HTTPS to allowed hosts (`packages/secret-proxy`); `varlock` uses the Varlock CLI; `env` exposes the value. Tool results always show placeholders.

## Skills, instructions, plugins and MCP

Bot-local sources win, then configured shared sources, then Pi's global ones; shared sources need the bot's inheritance flag. A bot-local skill named in the bot's `disabledSkills` is left out of the prompt, the `$` list and expansion, and its files stay untouched. Order and file names: `runtime/src/services/skill/`, `runtime/src/services/instruction/instruction.constants.ts`, `server/src/services/mcp/mcp-files.utils.ts`.

- A configured shared skills folder that does not exist (the default `~/.agents/skills` often does not) is skipped without a warning.
- MCP credentials are referenced by name (`envCredentials`, `headerCredentials`), only from shared sources; bot-local definitions that use them are skipped.
- `mcp.add` and the `bot_mcp_add` tool write `data/bots/<botId>/mcp.json`, which may use credentials: a header secret must be allowed for the server's host, and only the owner can pass env secrets to a command server. `bot_mcp_add` and `bot_note` always ask the owner, except under Full.
- MCP OAuth (`runtime/src/services/mcp-auth/`): the server URL always comes from bot config, the one-time `state` authorizes the callback browser, and `returnUrl` must be an app link or the redirect's own origin.
- Plugins are trusted native code; approval gates their tool calls, not their imports.

## Peers and subagents

Peers talk in one persistent private conversation per sender and recipient by default (`context: 'private'`; a new one starts after the sender's history is cleared); `context: 'existing'` posts into the recipient's main chat instead. Forwarding stops after three bots. Subagents cannot spawn children or contact peers. Silent answers are dropped before reaching the asking bot.

## Routines

One Pi task per routine ends each wait in a stored sleep, with no model calls (`runtime/src/services/routine/routine.task.ts`). Pi cannot wake a sleeping task early, so run-now and edits replace the routine's task in the same commit and abort the old one; a task that is delivering is left alone. A task that is no longer its routine's task ends itself. Opening a bot retries routine tasks Pi parked at its restart limit. After downtime an overdue run happens once; missed repetitions are skipped. Each store arms one host alarm at its earliest deadline, so the daemon must stay running.

## Silent replies

Assistant text that is only `NO_REPLY` or `<|eos|>` (`replySilent` in `contracts/src/types/reply.types.ts`) is hidden in chat, ignored by the chat-list preview and notifications, and dropped from peer and subagent answers. The reactions prompt asks bots to reply `NO_REPLY`.

## History clear

`conversation.clear` saves routines, todos and the latest artifact versions to `data/bots/<botId>/carry.json`, replaces the store and recreates them with the same IDs; a crash mid-way finishes on the next start.

## Hub (team installs)

`apps/hub` is the only public origin, behind Cloudflare Access. Every request needs a valid Access JWT (`Cf-Access-Jwt-Assertion`, else the `CF_Authorization` cookie): RS256 against `ACCESS_TEAM_DOMAIN/cdn-cgi/access/certs`, issuer, `ACCESS_AUD`, expiry with 60 s leeway, and an `email` claim. Failures are empty 401s; a valid identity without a user is an empty 403, except for a browser page load (GET or HEAD with `Accept` containing `text/html`), which gets the hub's own static 403 page (`core-refusal.native.ts`): the signed-in email, why (no user, or not an admin), whom to ask, and a sign-out link to `/cdn-cgi/access/logout`. An admin who is not a user loading any other page is sent to `/admin` (303). No script, `default-src 'none'`. Only `/hub/health` and the icon files `/favicon.ico` and `/img/favicon/<file>` (GET or HEAD, one segment) skip it; the icon files reach the web app without cookies or token, and anything else under `/img/favicon/` needs identity. A path with an empty or dot segment (`//rpc`, `/a//b`) is a 400 before routing.

```text
HUB_DATA_DIR/
  users.json   {"users": {"<email>": {"id", "daemonUrl", "socketPath"}}, "template": {"daemonUrl", "socketPath"}}; email, id, daemonUrl and socketPath each unique; reread within a second of a change
  admins.json  {"admins": ["<email>"]}: who may use /admin; seeded from HUB_ADMIN_EMAILS while empty or missing; written only by the hub
  pins.json    user id -> daemon server ID, written on first contact; a server ID belongs to one user only (the template's id is `template`)
  global.json  per user and settings section: follows the template (`global`) or not, and the last copy's result
```

- A missing, unreadable or invalid users.json means zero users: every identity gets 403 and the hub logs an error until the file is fixed. Fail closed, never the last good file.
- `/rpc*`, `/health`, `/files/*`, `/avatars/*`, `/embed/*` and `/mcp/callback` (HTTP and WebSocket) go to the user's `daemonUrl`; everything else goes to `HUB_WEB_URL` with the verified token in `Cf-Access-Jwt-Assertion`. Client identity and forwarding headers are stripped; `X-Forwarded-Proto` and `X-Forwarded-Host` come from `HUB_PUBLIC_URL`; `Origin` passes through. A relayed `Location`, `Content-Location` or `Refresh` URL that resolves to `HUB_WEB_URL` or the daemon URL is rewritten onto `HUB_PUBLIC_URL`, so no internal address reaches the client. `/files/*` without `Authorization` gets the device token from the `bots.connection` cookie.
- An open WebSocket is rechecked every 5 s and closed (1008) once its Access token has expired or its user is gone from users.json.
- Before forwarding, the daemon's `/health` must report the pinned server ID (checked at most every 5 s and on every address change), and a new pin may not equal another user's. A mismatch is a 502 and an admin-facing log line; nobody changes `pins.json` until the admin has confirmed which daemon belongs to whom.
- `socketPath` must be the real path: the hub refuses a socket that is a symlink or sits below a symlinked folder, before connecting.
- `GET /connect` without `code` mints a grant whenever the request has no `bots.connection` cookie for this user's daemon, including after `?reason=revoked|replaced`: it checks the grant's server ID against the pin and redirects to `/connect?code=<payload>`. `/hub/pair` does the same on demand. Before each grant the hub calls `onboarding.complete` on the owner socket: an admin set the workspace up, so the person is never asked to configure a provider, model or bot. At most 5 grants per user per 10 minutes, which also ends any redirect loop. `/hub/whoami` returns the email, user id and pinned server ID.
- Each daemon only receives its own user's traffic, so its peer-keyed throttles count one user's devices and hub calls together, never the whole organization.
- `/admin` and every path starting with `/admin` belong to the admin panel and never reach a daemon or a user route. They need an Access identity listed in `admins.json` (else 403; 401 without a valid JWT). A malformed or unreadable `admins.json` means no admins, logged as an error; the hub never seeds over it. An admin who is not a user gets only `/admin*` and GET/HEAD on the web app's static files (`ADMIN_WEB_FILES` in `core-server.native.ts`: `/assets/*`; the favicon paths are public anyway); everything else is 403. `/admin` and `/admin/*` pages go to `HUB_WEB_URL` with the verified token; unknown `/admin*` paths are 404.
- Admin API (`/admin/api/*`, JSON, `Cache-Control: no-store`): `GET me`, `GET|POST admins`, `DELETE admins/:email` (409 for the last admin), `GET|POST users`, `PATCH|DELETE users/:id`, `GET users/:id/avatars/<file>`, `POST users/:id/rpc/*` and the global settings routes below (other methods 404). Every non-GET request and every relay request needs `Origin` equal to `HUB_PUBLIC_URL` and either `Content-Type: application/json` or an `X-Bots-Protocol` header, else 403. Invalid bodies are 422. Admin and user changes return `access: 'synced' | 'manual'` from the provisioner: `manual` when the allow policy needs a change Orbs could not make (no token on the server, or the sync failed); without a token, a change that only touches emails inside the domain rule (`CLOUDFLARE_ACCESS_DOMAINS`) is `synced`, since there is nothing to change. `GET users` items and `GET admins` items carry `access: 'allowed' | 'not-allowed' | 'unknown'`, and `GET users` adds `accessMode: 'emails' | 'domain' | 'unknown'` and, for `domain`, `accessDomains`. They come from the provisioner's `GET /access` (`{ domains, emails }`; `emails: null` when it has no token, cannot read Cloudflare, or the policy has rules Orbs does not manage, and `domains` then come from `CLOUDFLARE_ACCESS_DOMAINS`), cached 15 s and dropped after every change; any failure, or no provisioner, is `unknown`, never an error for the list. Every admin write is logged with the admin's email, the action and the user id, never bodies.
- Users come from the provisioner (`PROVISIONER_URL`, `Authorization: Bearer PROVISIONER_TOKEN`; the hub refuses to start with a URL and no token). The hub's `admins.json` is the one admin list: the hub sends it to the provisioner (`PUT /access/admins`) at start, retrying for about a minute while the provisioner starts, and after every admin change, so the Access allow list follows it. A failed provisioner change is logged with the provisioner's error body and answers 502. The hub derives a new user's id from the name (else the email's local part), unique against current users and every pinned id, so a new person never reattaches a kept volume. Without `PROVISIONER_URL`, user changes answer 501 `{ "error": "provisioner_not_configured" }` and `GET users` lists `users.json` with `state: 'unknown'`.
- Template workspace: `users.json` may hold `"template": {"daemonUrl", "socketPath"}`, a daemon with no email that no login reaches; its addresses count in the uniqueness check, and no user may have the id `template` (the file is then invalid). `users/template/rpc/*` relays to it like a person; it never appears in `GET users`, and a new user's id is never `template`.
- Global settings: `GET global` -> `{ sections: [{ id, procedures }], state: 'ready' | 'starting' | 'missing' }` (`missing`: no template in `users.json`; `starting`: its `/health` does not answer). Sections and their relay procedures (an entry ending in `/` is the whole area): `models` `providers/`, `models/`; `chat` `conversation/settings`, `conversation/configure` (busy mode, hide tool calls and GIFs: one procedure holds them, and the Chat tab holds all three); `tools` `tools/settings`, `tools/configure`; `secrets` `secrets/`, `credentials/`; `sources` the `settings` and `configure` of `skills`, `instructions`, `plugins` and `mcp`. A section procedure whose last segment is `list`, `settings` or `session` reads; every other one writes. Bot procedures are in no section.
- `HUB_DATA_DIR/global.json` `{"users": {"<id>": {"<section>": {"mode": "global" | "overridden", "sync": "in-sync" | "pending" | "failed", "error"?}}}}` is written only by the hub (whole file, in order); it is not re-read while a save is queued or writing, so a reload never drops a pending save. A user or section missing from it is `overridden` (people added by hand or before global settings keep their values). Unreadable or invalid means no mode can be trusted: relay writes to any person's section procedure, mode changes, `global/sync` and user creation answer 503 `{ "error": "global_state_unreadable" }` and the hub logs an error; reads still work; it recovers once the file is fixed.
- `GET users/:id/sections` -> `{ sections: [{ id, mode, sync, error? }] }`; `PUT users/:id/sections/:section { mode }` -> the same shape for that section (`global` copies the template's values in before answering, `overridden` only flips the mode); `GET global/status` -> `{ users: [{ id, sections }] }`; `POST global/sync { section? }` copies that section (or all) to everyone who follows it and answers with the status. Unknown user or section: 404.
- A relay write to a person's daemon on a section in mode `global` is 409 `{ "code": "SECTION_FOLLOWS_GLOBAL", "section" }`. A successful relay write to the template on a section copies that section to every person in mode `global` in the background; saves that land during a copy run it once more, so the last save reaches everyone. Copies to one person run one at a time, and a multi-section copy reads each section's mode again just before copying it, so an override saved meanwhile is skipped and kept; one failing daemon does not stop the others. A person without a running daemon (disabled) stays `pending`; enabling them (`PATCH users/:id { enabled: true }`) copies every section they follow. A failed copy stays `failed` with the error until the next sync.
- A copy reads the template and writes the person with the forms' procedures, plus the owner-socket-only exports for what the forms cannot read: `models` is `providers.export` then `providers.import`; `chat` `conversation.settings` then `configure`; `tools` the settings plus `tools.export` into `tools.configure`; `secrets` the mode, then removes the person's secrets the template does not have and saves each template secret with its value; `sources` replaces `~/.agents` with `workspace.export`/`import`, then copies the four path lists. Values cross the hub in memory only; it never logs or stores them.
- `POST users { name, email, bots? }` sets every section of the new person to `global`, copies them, then copies the listed template bots before answering; the reply gains `bots: [{ from, botId | null, error? }]`. `POST users/:id/bots/copy { bots }` -> `{ bots: [...] }` later. A copy is `bots.get` and `bots.exportFiles` on the template, the avatar image fetched from the template's public `/avatars/<id>.webp` and uploaded with `avatars.upload`, `bots.create` with the same fields (a new id; a taken handle fails that copy), then `bots.importFiles`, deleting the new bot if that fails, so a failed copy leaves nothing behind and can be retried; derived MCP header values travel only to someone whose `secrets` section is `global`.
- `users/:id/rpc/<procedure>` relays HTTP to that user's owner socket at `/rpc/<procedure>` (the private door). The procedure must be plain path segments (`[A-Za-z0-9]`, no encoding) and never `pairing/*`, so no admin can mint a device, nor one of the owner-socket-only export and import procedures, so no secret value reaches a browser. Only `Content-Type`, `Accept` and `X-Bots-Protocol` are forwarded; the hub sets `X-Bots-Server-Id` to the pinned server ID, so a socket that belongs to another daemon refuses the call. Origin, cookies, `Authorization` and the Access JWT never reach the socket. Replies carry only `Content-Type` and `Content-Disposition`. The owner socket checks (real path, is a socket, no symlinked folder) are shared with the pairing hand-off.
- `users/:id/avatars/<file>` serves that user's `/avatars/<file>` (`<uuid>.webp` or `bots/<uuid>.png`, else 404; `template` too) from their pinned daemon with `Cache-Control: private, no-store`, never the daemon's public caching, because the hub routes `/avatars/*` by the viewer's own identity. The panel's per-user RPC context maps `/avatars/…` image sources there at display time (`avatarSrc`); stored avatar values never change.
