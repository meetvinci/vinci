# Vinci backend reference

Only behavior the code does not make obvious. RPC names and inputs: `packages/contracts/src/rpc/rpc.router.ts`. Services: `packages/server/src/services/<domain>/` (product) and `packages/runtime/src/services/<domain>/` (Pi).

## Daemon and storage

A daemon runs in its own container in an install (`/data` is its `DATA_DIR`). It runs natively only for development (`bun run dev:web`) and, until it becomes a window on an install, inside the desktop app. Its CLI is `vinci start` and `vinci pair`.

```text
DATA_DIR/                     default ~/.config/vinci/
  agents/<botId>/             bot working folder, uploads in .attachments/ (not a sandbox)
  data/app.sqlite             app database
  data/credentials.key        key for the encrypted credentials table
  data/avatars/               uploaded bot avatar images (`<id>.webp`) and each bot's rendered `bots/<botId>.png`, served at `/avatars/*`
  data/daemon.lock            one lock for every store
  data/ipc/rpc.sock           owner-only socket (the private door): `vinci pair` and admin settings
  data/bots/<botId>/runtime.sql   that bot's Pi store; the file is the unit of erasure
  data/bots/<botId>/mcp.json      MCP servers the owner or the bot added for that bot only
  data/bots/<botId>/telemetry.sql model and tool spans, kept 14 days; reset with the store
```

- Startup opens and migrates SQL, restores every bot, then resumes Pi. A failing store closes only its bot. A bot that cannot be configured at start (its folder cannot be made, a damaged file) is logged and skipped: it is not registered with the runtime, has no conversation in the list and answers `NOT_FOUND` until the next start or until its settings are saved; the daemon and the other bots start.
- Bot sandbox (every Docker install): with `DAEMON_SANDBOX_DIR` set, the Harness `env` (`runtime-env.utils.ts`, `runtime-sandbox.utils.ts`) is pi-env's `RemoteExecutionEnv`, so Pi's `read`, `write`, `edit` and `bash` run in the person's sandbox container, which sees `agents/` at the same path, `home/.agents` read only and the shared folder read only. The daemon listens on `exec.sock` there; the sandbox keeps a connection waiting, and pi-env's `Connection` reaches it through a bridge child and a private socket in the daemon's `tmpdir()` (pi-env only spawns a command for its transport): the daemon's own Bun runs `entry-sandbox-bridge.native` next to its entry (`runtimeSandboxBridgeRun`, `runtime-sandbox-bridge.utils.ts`, a 7 KB bundle). Everything from the sandbox is untrusted, and pi-env's client has no limits of its own to set (it buffers frames up to 16 MiB and reads a file of unknown or claimed size whole), so the bridge passes only: the sync line after at most 64 KiB of noise, frames up to 1 MiB, a `pread` reply no longer than asked, at most 10 MiB read through a file opened for positional reads (Pi's `read`, which reads an image whole) and 5 MiB through one opened whole (`mode: 'read'`: pi-env's `readFile`, which `edit` uses; the bridge learns which handle is which from the daemon's `open` request and the sandbox's reply; a reply naming a handle that is still open ends the connection, so the sandbox cannot move a file to the larger cap); more gets an `EFBIG` error frame, so the tool refuses the file and the bot uses bash, at most 4 MiB/s on average (the socket pauses: the sandbox waits, the daemon neither buffers nor spins). Anything else ends the connection (`sandbox bridge: …` in the daemon log, `ui_sandbox_lost` for the bot). Before Photon decodes an image for `read`, the daemon's image service reads its pixel size from the header and refuses over 8.3 MP, one decode at a time (`runtimeImageService`, team-workspace gotcha 327). `read` of a `.pdf` (`runtimePdfReadTool`, `runtime-pdf.utils.ts`) runs poppler's `pdfinfo` and `pdftotext` where the tools run (the sandbox image has `poppler-utils`), writes the text to a temporary file there and hands that to Pi's own `read`, so offset, limit and truncation work as for text; a password-protected, damaged, text-less (scanned) or too slow (60 s) PDF gets an error result that says so (a PDF bomb gets pdftotext OOM-killed in the sandbox in seconds: `exit code 137`), the last with a `pdftoppm` command to render pages as images; no PDF byte crosses the bridge. Command output needs no bridge limit: Pi keeps only a 50 KB tail (`OutputBuffer`) and pi-env paces it to 100 KiB/s; pi-env spills the full output to the sandbox's `/tmp`. One pi-env process serves every bot. Without a connection within 10 s a tool call fails with `SANDBOX_UNAVAILABLE`; a call in flight when the sandbox goes fails at once, its `pi-env connection lost` diagnostic (and `exited with code … before it was ready`, `did not answer within 60 s`, `Corrupt frame from pi-env`, all `RUNTIME_SANDBOX.lost`) rewritten by the `coding-tools` extension's `afterTool` hook (`ui_sandbox_lost`), and the next call reconnects. Tools never fall back to the daemon. The daemon then loads no plugins from bot folders or from shared plugin folders inside `agents/`, reads no MCP file inside `agents/` and does not even resolve a bot's own `.agents/mcp.json` or `.pi/mcp.json` (a link there could name another bot's owned file in `data/` or `/dev/zero`; a diagnostic says why), skips a bot instruction file that leaves the bot folders, is not a plain file or is over 1 MiB (with a warning; the turn goes on), and hands Pi's `loadSkills` a bot's skills only as private copies, in a temporary folder of the daemon container, of the files `runtimeBotFiles` found and read (1 MiB cap), never the folders or the bot's own files (Pi re-opens paths with no type or size check and walks links to folders: gotcha 235). Without the variable (development) tools run in the daemon through `NodeExecutionEnv` and none of these guards apply.
- Bot folders (`runtime-bot-files.utils.ts`, every install): the daemon reads and writes `agents/` (and `~/.agents`, which a bot could change before the sandbox) only through `runtimeBotFiles*`. A read opens the path and accepts it only if the kernel's name for the open file (`/proc/self/fd/N`) is inside the allowed roots, it is a regular file with one link, and it fits the caller's size cap (1 MiB for skills and instructions); `O_NONBLOCK` keeps a FIFO from blocking. Folders are opened one name at a time from the root, each checked the same way, and names below an open folder are looked up through `/proc/self/fd/N/<name>` (Node has no `openat`), so a link or folder a bot swaps in later cannot move a read, write, listing or removal out of the roots; links that stay inside are followed. Writes create with `O_NOFOLLOW` and refuse to write into a special file or a hard link; removal never follows a link. Refused means `FORBIDDEN` (a size over the cap `VALIDATION_ERROR`); callers skip the file and say so where a person or admin sees it. Users: skill expansion, argument hints and status, instruction files, workspace and bot file export and import, bot folder creation and removal, attachment upload, download, poster, removal, sweep and send, and MCP downloads. ffmpeg gets the video on stdin from a checked descriptor and returns the poster on stdout. A sandboxed bot sends files only from `agents/` and `~/.agents`. Outside Linux (development) the same checks use the resolved path and are not race-free.
- Disk full: an attachment upload that hits `ENOSPC` or `EDQUOT` (the person's sandbox disk, which holds `agents/`) removes the partial file (through `runtimeBotFilesRemove`) and fails with `DISK_FULL` (507); the app shows `rooms_files_disk_full`. `bots/create` makes the bot's folder inside the transaction that inserts its row, so a full disk (`DISK_FULL`, `rooms_bot_create_disk_full`) or any failed mkdir leaves no row; a copy's file import maps the same codes to `DISK_FULL`. A bot's own writes get the system's `No space left on device`.
- Command-type MCP servers run in the same sandbox (every Docker install). pi-mcp's `StdioTransport` only spawns a local child and pi-env runs long-lived programs only in a pseudo-terminal, so the MCP client gets `mcpTransportSandbox` (`runtime/src/services/mcp/mcp-transport.utils.ts`): pi-mcp's stdio framing (one message per line, a server that stops reading cut off) with `mcpMessage` (`mcp-message.utils.ts`): a message is kept whole up to 16 MiB; a longer one is read as a stream and never kept, and when it answers a pending `tools/call` it becomes that call's result, the head of its first text item (`result.content[i].text` only) bounded by Pi's tool output limits with the harness's truncation notice, counting every other byte of the message as dropped. HTTP servers get the same through the `fetch` given to pi-mcp's `StreamableHttpTransport` (`mcpMessageFetch`: a JSON body as one message, an event stream line by line, a failed answer's body cut to 4 KiB) over a spare `exec.sock` connection. The daemon's first line on it is `run <count> <fields>` (each field base64 of `v` and the value: working folder, `NAME=value` env entries, command, arguments; `runtime-sandbox.utils.ts`); `deploy/docker/sandbox.sh` answers `started` and runs the server with `setsid` as its own process group, or `missing` when the command is not installed there. The group is killed when the server exits or its connection ends (socat sends the script SIGTERM). The sandbox keeps one spare connection: the connection a start claims signals the dial loop (USR1) to open the next. Servers start on demand, as before; a closed connection (daemon or sandbox restart, server exit) is started again by the next preparation. No sandbox within 10 s gives the server the `ui_mcp_sandbox_unavailable` error, a missing command `ui_mcp_sandbox_missing`, both shown in the MCP catalog's diagnostics; a failed reconnect keeps the server's last tool definitions registered, answering with that error; a call cut off answers `ui_mcp_server_stopped`. Nothing falls back to the daemon. The server sees the sandbox's view, limits and network, and its env (secrets included) is readable by that person's bots (same uid).
- The daemon has no backup command. Docker installs back up whole volumes with `deploy.ts` (`docs/install/admin.md`, "Backups"); for a development data folder, stop the daemon and copy the folder (it holds `credentials.key`: treat the copy as a secret).

## Connection

- Clients probe every address from `server.info()` and use the first, in list order, whose `/health` reports the paired server ID (`server/src/services/server/`). The web server's probes of cookie addresses never follow redirects; native clients' probes do.
- `DAEMON_PUBLIC_URLS` replaces the detected loopback, LAN and Tailscale addresses with those origins (kind `public`); owner-added custom addresses still follow. Public origins are allowed browser Origins and CORS origins. No daemon issues a pairing grant or prints a PIN at startup: a hub pairs browsers over the owner socket, and `vinci pair` prints a PIN, link and QR code on demand (the desktop app pairs itself this way).
- Every call sends `x-bots-protocol`; `serverId` pins a client to one daemon. Mismatches return `PROTOCOL_MISMATCH` or `SERVER_MISMATCH` and are never retried.
- Pairing uses a six-digit PIN that lives five minutes; the QR code and link are Base64 of `{ serverId, addresses, pin }` (`authPairEntry` in `contracts/src/types/auth.types.ts`). Redeem returns the server ID and addresses, so a bare PIN works against a known address. Every wrong PIN counts against all live grants, which die after five misses. Public transport can never bootstrap; only the owner socket can.
- The web proxy only forwards to an address that reports the paired server ID, so a forged cookie cannot redirect it.
- Hub mode (`WEB_HUB_URL`): the hub routes daemon paths by the checked login, so the web server answers 404 for `/rpc`, `/health`, `/files`, `/avatars` and `/mcp/callback` and never reads cookie addresses. Any other request without the `vinci_session` cookie, other than a static file, gets an empty 401 (`Cache-Control: no-store`), as the hub answers it: the hub forwards every page with the token, so only a direct request to the web container lacks one. SSR sends RPC to the hub with the request's `vinci_session` cookie (`connectionAccessHeaders`). The browser keeps same-origin `/rpc`.
- The admin panel (`/admin`) renders only in the browser and never reads the pairing cookie. It calls the hub's `/admin/api/*` and sends a user's RPC over HTTP to `/admin/api/users/<id>/rpc`, which the hub relays to that daemon's owner socket. It keeps its own query client, and its query keys start with `admin-user:<id>`. Global settings and suggested bots are the same screens pointed at the reserved id `template` (`/admin/users/template/*`); a person's sections that follow global are shown read-only, and the hub's 409 `SECTION_FOLLOWS_GLOBAL` on a relay write becomes a message, not a lost connection. The Conversations tab reads a person's chats with `conversation.list`, paged `conversation.history`, `conversation.search` (on Enter, one call per bot), `conversation.reactions` (one call per history page), `tools.pending` and `conversation.questions` (once per open chat, for what waits for the person), and `artifacts.get` and `artifacts.versions` (only when the admin opens an artifact), plus the wave-1 reads `bots.list` and `conversation.settings`; nothing else. No `watch*` stream, no polling, no focus or reconnect refetch: the hub audits every conversation read, so those keys of that person fetch on open and on **Refresh** only. A subagent run or a private bot-to-bot chat opens in a pane read with `conversation.history` by its `conversationId` (from the tool call; the private one from the recipient bot). The panel renders the app's transcript with `isReadOnly` and `sectionScope.isAdmin`, which drop every write control and every other read: no reactions toggle, reply, stop or live subagent; an artifact card opens a pane that reads the version its tool call names (`artifacts.get` with `version`) and lists the others (`artifacts.versions`), rendered by the app's `ArtifactView` without a store, so json-render keeps interactions in memory and nothing calls `artifacts.saveState`, `update` or `restore`; the viewer is wrapped in `OutsideContentPolicy` (`@repo/ui/outside-content`), so nothing in it loads from another origin: `HtmlFrame` renders with `sandbox=""` (no script, so no WebRTC, no self-navigation, no meta refresh; the frame's CSP stops the rest; the theme tokens are written into the document, `htmlFrameTheme`, since no script receives the theme message), an artifact **Image** block and a markdown `img` whose source is not `data:` or `blob:` render a placeholder, and each `OutsideContentGuard` (the artifact pane, and every `Response`, which wraps itself in one) shows one notice when something inside was held back (a page with script, links, frames or templates counts, `htmlHasOutside`; while held it also goes through `htmlInert`, which drops `link`, `iframe`, `frame` and `template`, since Chrome connects for them before CSP or sandbox refuse; a markdown `source` and a reaction GIF are held too); its **Load outside content** awaits `POST /admin/api/users/<id>/outside { botId, conversationId }` before that one artifact or message renders as in the app (`sandbox="allow-scripts"`, remote images), until it unmounts; a waiting approval or question shows as a read-only card in the transcript's footer, and an approval also marks its tool step (matched by tool name and arguments, as history carries no task id); routine and todo chips make no list query; and the RPC context's `hasLinkPreviews: false` turns off `links.preview` and the third-party favicon of each link (`LINK.faviconUrl`), so the admin's browser makes no request that names a link's host. The context's `fileSrc` maps attachment paths (`/files/<botId>/<attachmentId>[/poster]`, nothing else) to `/admin/api/users/<id>/files/…`, so images and media never use an RPC download or the person's public door; that route adds `X-Bots-Protocol` itself, since an `<img>` sends no headers.
- A hub hands a code it issued to `/connect?code=<pairing payload>` (`connectionSearch`); the page drops it from the URL. A link code (`?code=` or `#code=`) is redeemed at once with the default device name only when every address in it is the page's own origin, in the desktop shell, or in hub mode (the route's loader reads the hub's whoami; the hub picks the daemon by identity, so the code's addresses decide nothing there and the page shows *Opening your workspace* with no PIN form, or **Try again**, which asks the hub for a new grant); any other code is only prefilled for the user to confirm, so a crafted link cannot pair a browser to a foreign server.
- A redirect answering the web client's `/health` check means a login gate's session expired: the page reloads at most once a minute so the gate can sign the user in; unsent drafts live in `localStorage`. The PWA manifest and its icons stay under `/img/favicon/` (plus `/favicon.ico`) so a gate can exempt them.
- Development (`bun run dev:web`, `scripts/hub.ts dev`) runs the daemon, a hub and Vite (`WEB_HUB_URL`) behind a dev door on the first port that plays the Laravel API's login: it answers the hub's `/internal/session` (the hub's `HUB_ACCOUNTS_URL`, with a per-run `HUB_ACCOUNTS_TOKEN`; `PUT /internal/users/*` answers `{ created: false }`, other account routes 404) and 401 to any other request without a `vinci_session` cookie, localhost included (every container on the Mac reaches it as 127.0.0.1); `/auth/logout` clears the cookie. Every browser logs in once with the per-run link the script prints, which sets a 30-day cookie for `dev@example.com`, a hub user and admin: a Sanctum-shaped token kept in `<data>/hub/dev-session`, which the hub checks with the door. With `--url <origin>` the door listens on every interface for other devices. `--data` is resolved to its real path, since the hub refuses an owner socket below a symlink. Ports: door, daemon, hub, Vite from `--port` (47190). `--sandbox` sets `DAEMON_SANDBOX_DIR` to `<data>/sandbox` and runs the `vinci-sandbox:dev` image with the bot folders and that folder at the daemon's own paths; a relay in it makes `exec.sock` and `proxy.sock` in its own `/run/sandbox` and relays them over TCP to `host.docker.internal` on the next two ports, where the script connects each connection that starts with the run's key to the daemon's socket. A stand-in `firewall-wait` lets it start without the firewall. Vite's HMR socket goes to Vite's own port, because the hub relays no WebSocket to the web app. The hub has no switch for the door, and the hub image bundles only `apps/hub/src`.
- The connect page redeems one code once: a link both fills the PIN (which fires the PIN field's completion) and submits itself, and a second redeem of a used PIN fails as `UNAUTHORIZED` and counts as a wrong PIN against every live grant.

## Owner socket (private door)

`data/ipc/rpc.sock` (0600 in a 0700 folder) serves the oRPC router over HTTP `POST /rpc/*` with the same request and response shapes as the public door, to the owner without a device. It exists so an admin (through the hub) and `vinci pair` can manage a daemon, and read its conversations, without pairing as a device.

- Only the procedures in `RPC_LOCAL_ALLOWLIST` (`server/src/rpc/rpc-local.utils.ts`) are served; every other procedure, including any added later, answers `FORBIDDEN` (403) before throttles or handlers run. A request with an `Origin` header is a 403, anything that is not `POST /rpc/*` (WebSocket upgrades included) a 404. Bodies are capped at the avatar size plus 1 MiB (9 MiB), for `avatars.upload`.
- Served: server info and addresses, daemon chat and notification settings, providers and models, plugins, instructions, skills, MCP and MCP OAuth, tool settings, the MCP servers and tools for the approvals screen (`tools.servers`) and the person's own approval changes (`tools.control`, `tools.trust`), secrets, credentials, bots (list, get, catalog, create, update, delete, model swap), avatar upload, `commands.execute` only for `reset` without handoff text, each bot's routine and todo lists (read only), devices (list, revoke), `pairing.bootstrap`, `transcription.settings` and `transcription.configure`, and the rate limits (`limits.settings`, `limits.configure`, on `ownerRouter` so the socket reaches them; the input bounds below hold for every caller).
- Served for the admin's read-only conversation viewer, and only what it uses: `conversation.list`, `history`, `search`, `reactions` and `questions`, `tools.pending`, `artifacts.get` and `artifacts.versions`, plus `attachments.download` and `poster` for the hub's admin file route (the hub's relay refuses `attachments/*`). Each only reads: preference rows, the bot row, Pi documents, entries and the task graph (`snapshot`, `entries`, `taskGraph`, disposed after use), and attachment files; nothing marks read, arranges, answers or bumps a timestamp. `conversation.list` reads only open stores; any other read reopens a store that failed and closed, as every request and the alarm already do. Not served, because the viewer does not use them: `conversation.contexts`, `artifacts.list`, `listBot` and `blocks`, `activity.*`, `attachments.list` and `links.preview` (which would make the person's daemon fetch an address the admin chose; it fetches live and stores nothing).
- Refused: every conversation and tool write (submit, edit, stop, clear, question and approval answers, reactions, read marks, arrange, pin, hide, mute, busy mode), every watch stream (the viewer reads over HTTP only, so a reply in progress shows on the next read), context and bot usage, the command list, `compact`, `retry`, `cancel` and handoff resets, creating, changing, running or deleting routines and todos (they belong to the user), `pairing.create` and `pairing.redeem`, attachment upload and removal, artifact writes, notification presence, push and Web Push (`webPushKey`, `webPush`), and sidebar sections.
- Owner socket only (`localRouter`, `FORBIDDEN` on the public door even with a device), for the team hub's global settings and bot copies, and refused by the hub's admin relay: `providers.export` (API keys stored in Pi's auth store, with their env values; never OAuth logins, env or `models.json` keys) and `providers.import` (makes the stored API keys exactly that list through Pi's own API-key login, answering its prompts with the key then the env values in order; signs out every other stored API key; OAuth logins stay), `secrets.export` (every secret rule with its value) and `secrets.import` (makes that list the daemon's global secrets: saves each with its value and `isGlobal: true`, removes the global secrets not in it, and keeps every secret without `isGlobal` except one with the same name as an imported one, which the global one replaces), `tools.export` (the Jev key or `null`), `transcription.export` (the voice input key or `null`), `workspace.export` and `workspace.import` (every regular file of `~/.agents`, base64, at most 2000 files and 6 MiB; import writes a sibling folder and swaps it in, so it replaces the folder, and puts the old folder back if the swap fails; links, hard links and special files are never followed but listed in the export's `skipped`, and `node_modules` and `.git` are left out), `bots.exportFiles` and `bots.importFiles` (a bot's instruction files at the top of `agents/<botId>/`, its `.pi/` and `.agents/` folders (links, hard links and special files listed in `skipped`, which the hub returns with the copy), and its own `data/bots/<botId>/mcp.json` with the header values derived for it, renamed to the new bot's id on import; import refuses any other credential key and reconfigures the bot).
- Handlers on the allowlist use `ownerRouter`, where `context.device` is `null` on the socket; everything else uses `authedRouter`, which still requires a device, so a listed procedure on `authedRouter` stays refused. Provider and MCP OAuth logins started on the socket belong to `deviceId: null`: only the socket can see, complete or cancel them, and revoking a device never cancels them.
- The public door is unchanged: every procedure except pairing redeem and bootstrap still needs a device token there. It also refuses a few changes to every device; see below.

## Team daemon refusals

Every daemon is a team daemon (one-mode piece H removed `DAEMON_TEAM`). Its public door answers `TEAM_MANAGED` (403, typed in the contract, shown by every client as `ui_team_managed`, "Your admin manages this.") to a device that would change one of: a bot's `permission` (`bots.create` with anything but `BOT_FIELDS.defaultPermission`, `normal`; `bots.update` with a different value), `tools.configure` `approvalRules`, `approvalTimeoutMinutes` or `policyDefaults` (compared with the stored values; the Jev key and the person's own `policy` still save), `secrets.configure` `mode`, `secrets.save` or `secrets.remove` of a secret marked `isGlobal` or `credentials.set` of its `secrets.<name>` key, `mcp.add` with `command` or `env`, any `mcp.replace`, a changed `models.configure`, any `transcription.configure` or `credentials.set` of its key, and any `limits.configure` (the admin changes limits on the person's **Devices** page through the socket). `limitConfigure` takes requests per window of 60-100,000 for `public` and `device`, 1-100 for `redeem`, a window of exactly 60 s (any other `windowMs` is refused, so the per-minute bounds can't be dodged with a longer or shorter window; a window stored earlier stays until a save sends 60 s, which every panel save does) and 4-1,000 for `rpcInFlight` and `watchInFlight` (`LIMIT_BOUNDS` in `contracts/src/types/limit.types.ts`); anything else is a 400. Unchanged values pass, so whole-form saves work. `rpcTeamRefuse` (`server/src/rpc/rpc-team.utils.ts`) runs in those handlers after authentication; the owner socket (`isLocal`) never refuses, so the admin keeps every one through the hub's relay, except `limits.configure`, which the owner socket has never served. The bot's own `bot_mcp_add` tool refuses a `command` the same way; other bot tools are unchanged. A daemon without a hub (the desktop app's embedded one) refuses the same: nobody there can change these until the desktop app becomes a window on an install.
- No peer-credential check: any process with the daemon's uid can call the socket, a bot's bash included (team-workspace risk 1).
- Stdio MCP servers, plugins and skills stay on the list: configuring a user's bots is what the admin panel is for. They run code inside the user's workspace, so an admin can technically read that user's data; admins are fully trusted, and the panel only offers no way to chat or answer as the user.

## Retries and dedupe

- `conversation.submit` dedupes by `requestId`: a reused ID returns the same submission even with new content. Clients never retry commands or submissions on their own.
- Peer delivery submits with `bots.delivery:<senderStoreId>:<taskId>`, so a rerun after a crash delivers once (`runtime/src/services/collaboration/collaboration-delivery.task.ts`).
- Tools that mutate use `replay: 'unsafe'`: after a crash, read state before retrying.

## Busy modes (`whenBusy`)

`followUp` queues after the reply, `steer` joins after the current tool round, `interrupt` aborts the run and goes first (`CONFLICT` if a newer run started), `reject` fails when busy. When omitted: the chat's mode, then the daemon default, then `followUp`.

## Model fallback

One retry on the bot's `fallbackModel` only when a request fails before any output with an auth, quota, transient provider or stall error (`runtimeModelStreamCanFallback` in `runtime/src/services/runtime/runtime-model-stream.utils.ts`).

## Model stalls and failing tool calls

- pi-ai's `timeoutMs` bounds a whole HTTP request and only in some adapters, so Vinci adds an idle timeout (`runtimeModelStall`, `RUNTIME_MODEL_STALL` in `runtime.constants.ts`): a request that sends no stream event and no raw provider event (`onProviderStreamEvent`) for 180 s is aborted (long enough for a reasoning model that streams nothing while it thinks). Before any output it is sent once more; after that, or after a stall mid-answer, the run ends with `MODEL_FAILURE.stalled` (`contracts/src/types/model.types.ts`), which Pi Durable does not retry and clients show as `rooms_event_failed_stalled` (*The model didn't respond. Try again.*). It wraps every provider request, fallback and compaction included; Stop still aborts at once.
- The `bots.tool-guard` extension (`runtime-tool-guard.extension.ts`) runs `beforeTool` ahead of the approval hook and reads the turn (everything after the newest user message) from the transcript: a call whose name and arguments (as the model sent them) already failed 3 times in a row, or any call after 10 failed calls in the turn, is blocked unrun with a reason that tells the bot to stop and explain (`RUNTIME_TOOL_GUARD`). Nested calls are not guarded. Since no Pi Durable hook can end a run, `runtimeToolGuardStream` ends it before the next model request once the turn has 3 such refusals, with `MODEL_FAILURE.toolLoop` (`rooms_event_failed_tool_loop`).

## Voice input (transcription)

One admin key, the credential `transcription.openaiApiKey` (named before reading aloud existed and kept so stored keys keep working), serves dictation and reading aloud; the panel and the docs call it the voice key.

`transcription/` (`server/src/services/transcription/`): `settings` -> `{ isConfigured }`, the only thing a client learns about the key; `configure({ apiKey | null })` stores or deletes the admin's OpenAI key as the encrypted credential `transcription.openaiApiKey` (owner socket only in effect: every device call is `TEAM_MANAGED`, and so is a `credentials.set` of that key); `export` (owner socket only, refused by the hub relay) gives the hub the key for the Tools copy; `transcribe({ file })` (any paired device, over HTTP RPC like attachment uploads: `client.ts` routes it off the WebSocket) takes one recording of at most `TRANSCRIPTION.maxBytes` (10 MiB, contracts; the daemon's body cap is 12 MiB) whose name ends in `.webm`, `.ogg`, `.mp4`, `.m4a`, `.mp3` or `.wav` (`TRANSCRIPTION.extensions`; Bun's multipart parser derives a file's type from its name and drops the part's `Content-Type`, so the format travels in the name, `recording.<ext>`), posts it to OpenAI's `/v1/audio/transcriptions` with model `TRANSCRIPTION_SERVICE.model` (`gpt-transcribe`, the provider's recommended model) and no language (the model detects it), and answers `{ text }`. The file lives only in the request's memory: it is never written to disk, and nothing logs the audio, the text or the provider's body (only its status). Failures are `TRANSCRIPTION_FAILED` (502) with `reason`: `unavailable` (no key, or a name without one of those extensions), `rejected` (the provider answered 401 or 403: a wrong or revoked key) or `failed` (anything else, including the 120 s timeout); a file over the cap or of another type is `VALIDATION_ERROR`. The ordinary per-peer RPC rate limits apply.

The web composer (`useChatDictation` in `client/src/hooks/use-chat-dictation.web.ts`, `rooms-chat-dictation.tsx`) shows the microphone only when `isConfigured` and the browser has `MediaRecorder` in a secure context. Recording keeps chunks in memory and stops itself at `TRANSCRIPTION.maxDurationMs` (5 minutes) and transcribes; Cancel or Escape stops the tracks and drops the chunks with no request. The text goes in at the editor's selection (`PromptInputEditorHandle.insertText`, which replaces a selection and puts one space first when the character to its left is not whitespace), and focus returns there. Send is disabled while recording or transcribing; nothing is ever submitted automatically. No install header sets `Permissions-Policy`, so the browser's default (`microphone` for the page's own origin only) applies; artifact frames are sandboxed without `allow-same-origin` and get no microphone. Mobile and desktop have no voice UI yet; the contract, `transcriptionProblem` (the shared error copy) and the client routing are where they will reuse it.

## Reading aloud (speech)

`speech/` (`server/src/services/speech/`): `speak({ text })` (any paired device, an event stream over the WebSocket like a watch, so it takes a `watchInFlight` lease) reads the voice key through `transcription.queries.export()` and answers `SPEECH_FAILED` (502) `unavailable` without one. `speechText` (`speech.utils.ts`) makes the reply ready for the ear by rule: a fenced code block becomes `[code block: <language>, <n> lines]`, link and image markup keeps its text, an address becomes `[link: <host>]`, HTML tags go, a list of more than 6 items keeps 4 and a table of more than 6 rows keeps 4, each with `[and N more ...]`. More than `SPEECH.maxSpokenChars` (6,000) after that is `tooLong`; the transport cap is `SPEECH.maxInputChars` (32,000, `VALIDATION_ERROR`). The driver (`speech.driver.ts`) opens one Realtime session per reply to `wss://api.openai.com/v1/realtime?model=gpt-realtime-2.1-mini` (the key travels as the `openai-insecure-api-key.<key>` subprotocol next to `realtime`, OpenAI's form for clients without custom headers; the DOM `WebSocket` type has none), sends `session.update` (audio output only, `audio/pcm` at 24 kHz, voice `SPEECH_SERVICE.voice` (`cedar`), `reasoning.effort: low`, no turn detection, instructions `speechPromptsReader`: speak the reply in its own language and only that, European Portuguese with a Lisbon accent for Portuguese unless the reply is Brazilian, never answer or add, describe code, sum up tables and long lists), one `input_text` user item with the prepared text, and `response.create`; each `response.output_audio.delta` is passed on as `{ audio }` (base64 PCM16 LE mono 24 kHz), and `response.done` with `completed` ends the stream. The `/v1/audio/speech` models (`gpt-4o-mini-tts`, `tts-1`) shut down on 2027-01-06; their documented replacement is this model on the Realtime API. Failures: an `error` event whose code is `invalid_api_key`, `insufficient_permissions` or `insufficient_quota` is `rejected`; any other error, a reply not `completed`, a closed or failed connection or the 120 s timeout is `failed`. Logs carry only those codes and statuses, never the text, the audio or the key. The client stopping the stream (abort) closes the socket. Nothing is stored; the text and audio exist only in the request. Served on the public door only (not the owner socket, not the admin relay).

The web player (`useChatSpeech` in `client/src/hooks/use-chat-speech.web.ts`, context `chatSpeechContext`, provided by `RoomsChatView`) shows the speaker button (`RoomsChatActions` `speech`) on assistant replies with text and the **Read replies aloud** toggle (`rooms-chat-speech.tsx`) only when `transcription.settings` says `isConfigured` and the browser has `AudioContext`. One reply plays at a time: each chunk becomes an `AudioBuffer` scheduled right after the previous one, so playback starts with the first chunk; stop aborts the stream and stops every scheduled source. The `AudioContext` is created or resumed inside the click on the speaker or the toggle (the autoplay gesture) and closed when the chat unmounts. The toggle is per open chat, in memory: on, it reads the newest finished assistant reply (not busy, entry id above the one present when it was turned on), and it is off again after leaving the chat or reloading. Submitting (send or stop), the stop shortcut and starting the microphone stop the speech. No audio is kept: replaying synthesizes again. A context that is not `running` when the audio ends (blocked autoplay) shows `rooms_chat_speak_blocked`. Error copy: `speechProblem` (`client/src/services/speech/speech.utils.ts`).

## Approvals

A bot's `permission` is one of three modes: `read-only` (the conversation's tools are `readOnlyTools` only, and authorization denies anything else), `normal` (the default, `BOT_FIELDS.defaultPermission`) and `no-questions` (allows every call). Migration `0010_bot_modes` maps `ask`, `sandbox` and `auto` to `normal` and `full` to `no-questions`, and folds every `tools.alwaysAllow.<botId>` list into the person's policy as allow controls with `server: null`, except MCP runtime names (`mcp_…`, not traceable to a server) and `bot_mcp_add`/`bot_note`, and deletes the old keys.

`toolActionAuthorize` (`server/src/services/tool/`) decides each call: no bot → deny; a trusted Vinci read-only registration (`isReadOnly`) → allow; `no-questions` → allow; `read-only` → deny; the bot's own tools (`isOwn`) → allow; an answered approval (`approved`) → allow. For `normal`, in order: `bot_mcp_add` and `bot_note` (`TOOL.askFirstTools`) ask; a control from the person's `tools.policy`, then from `tools.policyDefaults` (in each, the tool's control before its server's) allows or asks; a Pi coding tool with a sandbox (`isSandboxed`) runs; an MCP tool whose server is trusted and whose `annotations.readOnlyHint` is `true` runs; with a Jev key and at least one approval rule, Jev may allow it (safe score at least 0.9 and ask-first score at most 0.1, rechecked against the latest bot and rules, as before); otherwise it asks. A server is trusted when its key equals a `MCP_PRESETS` URL (`contracts/src/types/mcp.types.ts`) or is in the person's own `policy.trusted`; `policyDefaults.trusted` is never read, and the hub copies the template's `policy` with `trusted` emptied, since trusting a server is only the person's act. The runtime's MCP client keeps each connection's server name and key (the URL, or the command line for a stdio server, `mcpServerKey`) and the definitions aligned with its registrations; `mcp.queries.tool({ botId, name })` finds a runtime tool name's server and MCP definition, `mcp.queries.servers()` lists every connected server and its tools for `tools.servers`.

The policy (`toolPolicy` in `contracts/src/types/tool.types.ts`): `controls` (up to `TOOL_APPROVAL.maxControls`) of `{ server: key | null, tool: MCP tool name | runtime name | null, behavior: allow | ask }`, and `trusted` server keys. `tools.settings` answers both `policy` and `policyDefaults`; `tools.configure` writes either whole. The app changes one control or one trust at a time with `tools.control({ server, tool, behavior | null })` and `tools.trust({ server, isTrusted })`, which read and write the stored policy on the daemon, so a card's **Don't ask again** and a settings screen open on another device never overwrite each other. The hub's Tools copy sends the template's own `policy` (without `trusted`) as each person's `policyDefaults` and never touches their `policy`; its preview diffs it as `approvalDefaults`. A device may write `policy` while Tools follows global.

Approval state lives in Pi task documents and survives restart. `conversation.queries.approvals` adds `action` to each pending approval: `{ server, serverName, tool, canAllowAlways }`, looked up when read (an approval whose server has gone shows the generic sentence). Clients build the question's sentence from it (`toolApprovalSentence` in `client/src/services/tool/`): a hand-written template for a shipped server's tool (`TOOL_APPROVAL_SENTENCES`, keyed by URL and tool, with the argument keys that name the subject), else *Use {tool} on {server}*; the bot's text never goes into it. **Don't ask again for this tool** (`tools.answer` with `always: true`) saves an allow control for that server and tool in the person's `policy`; it is hidden and ignored for `bot_mcp_add` and `bot_note`. A request nobody answers before the timeout is blocked with `TOOL_APPROVAL.expiredResult` as the reason, a denied one with *Tool permission was denied.*; clients find that text in the tool's error and show the step as its own *Request expired* row (`toolBlocks` kind `expired`), which stays visible when tool calls are hidden.

Not classified (phase 2 of issue #37, an accepted risk): commands and HTTP requests from the sandbox, so a `curl` with a secret that has that access runs under `normal` without asking.

## Secrets

`bot_secret` stores values encrypted as `secrets.<NAME>` with allowed hosts. Bash reads `$NAME`. Mode `proxy` (default) keeps a placeholder in the command and swaps in the value only over HTTPS to allowed hosts (`packages/secret-proxy`); `varlock` uses the Varlock CLI; `env` exposes the value. Tool results always show placeholders. With a bot sandbox the proxy also listens on `proxy.sock` in the shared folder and writes its CA bundle there; commands reach it at the sandbox's `127.0.0.1:47195` (a socat forward). The bridge connects to the proxy from loopback, so the proxy trusts no peer for being local: every request needs the token. `varlock` mode needs the Varlock CLI in the sandbox, which the image lacks.

The proxy is the daemon's own HTTP server on `127.0.0.1`, on a free port, in the daemon's process (`secret-proxy-action.start.ts`): nothing else on the container's networks reaches it, and a sandbox reaches it only through `proxy.sock`. It replaced mockttp, which listens on every interface and could be crashed by one request (gotcha 230). It takes absolute `http://` requests and `CONNECT`; each needs the token as Basic proxy credentials (`bot:<token>`), and without them the answer is `407` with a `Proxy-Authenticate` challenge (the env still sets `GIT_HTTP_PROXY_AUTHMETHOD=basic`, which saves git that round trip). A `CONNECT` target with `*` or `%` gets 400, so no wildcard certificate is ever made. On `CONNECT host:port` it answers 200 and terminates TLS with a certificate for that name or IP, signed by a CA it makes at each start (`@peculiar/x509`, P-256; the bundle is in the secrets folder and the sandbox folder). Each request inside goes to `https://host:port` plus its path: the `CONNECT` target decides where it goes and which secret hosts it matches, never the `Host` header or SNI, and a request inside that is not origin-form (`/…`) gets 400. Clients that read `HTTPS_PROXY` go through the proxy (curl, git, wget, Bun `fetch`, npm, pip, uv, Python's `urllib`, `requests` and `httpx`, and Node 24's `fetch` and `https` because the env sets `NODE_USE_ENV_PROXY=1`); Bun's `node:https` and `node:http` ignore it and connect directly, carrying only the placeholder. Each trusts the proxy's CA through the env's CA variables, and wget through `WGETRC`, a `wgetrc` the proxy writes next to its bundle naming it. Placeholders are swapped in plain header values and the query string only, not inside base64 (`user:password@` URLs, Basic logins). The proxy verifies the destination's certificate, so an untrusted or wrong-name certificate gets 502 and nothing is sent.

Every authorized request, placeholder or not, then goes through the forward step in the same process (`secret-proxy.driver.ts`), which:
- Resolves the name once and refuses with 403 and a plain message when any answer is internal: the firewall's IPv4 ranges (private, CGNAT, link-local and metadata, loopback, benchmarking, multicast and reserved, which cover Docker's bridges) and IPv6 loopback, unspecified, IPv4-compatible, NAT64, 6to4, discard, unique-local, link-local, site-local and multicast, and IPv4-translated (`::ffff:0:0:0/96`); IPv4-mapped forms are checked as IPv4. It then connects to the checked address with the original name for SNI and certificate checks, so DNS rebinding between check and connect cannot happen. It follows no redirects: a client that follows one sends a new request, checked the same way. A `CONNECT` opens no upstream connection by itself: the proxy answers it and terminates the tunnel, and each request inside goes through this check. `VINCI_INTERNAL_ALLOW` (daemon env, the firewall's exact `<IPv4>:<port>` list) is the only exception.
- Scrubs every response from a host that any secret's rule allows, with the values of all those rules (a host may store a value and echo it later without a placeholder): the status message, header values (`Location`, cookies) and header names (in lower case, as they arrive) as strings, the body as a stream that holds back only a tail that could still start a match, so a value split across chunks is still caught at any size and a streamed event (SSE) goes on at once. Each form's next match is searched again only once the scan passes it, so a body dense with matches costs one pass per form. Forms: as is, URL-encoded (upper and lower hex), JSON-escaped, and base64 and base64url at all three alignments, which covers a Basic auth value of `user:<value>` (base64 forms only for values of 8 bytes or more). A gzip, x-gzip, deflate, br or zstd body, as `Content-Encoding` or as a transfer coding before `chunked` (`Transfer-Encoding: gzip, chunked`), is decoded and sent without `Content-Encoding` or `Content-Length`; any other encoding is refused with 502. A request to such a host loses `Range` and `If-Range`, so a value cannot be fetched in two partial pieces. Responses from hosts no rule allows stream through untouched.
- Drops trailers, hop-by-hop headers, `Expect` and the proxy credential. Ends a request after 60 s without a byte, or 20 minutes in all; a request cut after its headers looks to the client like a short body.

Bodies stream both ways with backpressure and are never held whole. The swap covers the query string and header values only: a placeholder inside a request body is sent as the placeholder, at any size. Bun's TLS socket over a `CONNECT` socket reports no backpressure to the response written on it, so for a tunnel the proxy waits for `drain` on the `CONNECT` socket underneath (gotcha 231). A malformed request, an oversized header, a hostile URL (a zone ID, a bad port), an invalid `CONNECT` target or TLS garbage after `CONNECT` fails only that connection: Bun drops what it cannot parse, the proxy answers 400 for a target it cannot use, a handler's error ends only its own response, and a connection idle for 60 s is closed (a tunnel by a timeout on its `CONNECT` socket, since Bun applies the server's timeout neither to that socket nor to the TLS socket inside it), and a tunnel or `proxy.sock` connection whose other side has closed is closed at once (gotcha 229). What the proxy cannot stop: a destination that transforms the value any other way (hashes, re-encodes, splits it) hands it to the bot's process, so allowed hosts must be ones the admin trusts with the value; tool results are still redacted. See gotchas 154, 220-223 and 230-235.
A secret rule may carry `isGlobal: true`: only the team hub's `secrets.import` sets it, and any other save of that name drops it. A team daemon refuses a device's save or removal of such a secret, or a `credentials.set` of its key (`TEAM_MANAGED`), and answering a bot's secret question with that name keeps the global value and stores nothing. Every other secret is the owner's own. The clients show global secrets with *From your admin* and no remove button. A daemon without a hub (the desktop app's embedded one) never has one.

## Skills, instructions, plugins and MCP

Bot-local sources win, then configured shared sources, then Pi's global ones; shared sources need the bot's inheritance flag. A bot-local skill named in the bot's `disabledSkills` is left out of the prompt, the `$` list and expansion, and its files stay untouched. Order and file names: `runtime/src/services/skill/`, `runtime/src/services/instruction/instruction.constants.ts`, `server/src/services/mcp/mcp-files.utils.ts`.

- A configured shared skills folder that does not exist (the default `~/.agents/skills` often does not) is skipped without a warning.
- `skills/status` -> `{ skipped: [{ path, reason, message }] }` lists the shared skill files (configured folders and Pi's agent folder, not bot-local ones) that Pi's `loadSkills` diagnostics name and did not load: `frontmatter` (the YAML header throws), `description` (none), `duplicate` (a name collision, the later file), `other`. Warnings on skills that loaded are left out; `message` is the diagnostic's first line. Settings → Sources shows them; on the owner socket it is allowlisted and the hub relays it quietly (`RELAY_QUIET` matches `*/status`).
- MCP credentials are referenced by name (`envCredentials`, `headerCredentials`), only from shared sources; bot-local definitions that use them are skipped.
- A server `url` is `https`, or `http` only when its host is an IPv4 address and `<address>:<port>` (80 when omitted) is in `VINCI_INTERNAL_ALLOW` (`mcpIsUrlAllowed`, checked by `mcp.add`, `bot_mcp_add` and `mcp.replace`; `validation_mcp_http` otherwise). The daemon itself connects, not the secrets proxy; the firewall lets it through for the same list. Shared MCP files in Sources are not checked.
- `mcp.add` and the `bot_mcp_add` tool write `data/bots/<botId>/mcp.json`, which may use credentials: a header secret must be allowed for the server's host, and only the owner can pass env secrets to a command server. With a bot sandbox those env values reach the server in the sandbox, where the person's bots can read them; tool results still show placeholders. `bot_mcp_add` and `bot_note` always ask the owner, except under Full.
- `mcp.get({ botId })` returns that file as stored (`{ mcpServers }`, credential references, never values); `mcp.replace({ botId, mcpServers })` replaces it whole (the admin panel's *Edit as JSON*, owner socket only) and answers the bot's catalog after reconnecting. Entries are `mcpFileServer` (contracts): a `url` with `headers`/`headerCredentials`, or a `command` with `args`, `cwd`, `env`/`envCredentials`, plus `description`, `enabled`, `disabled`; at most 32, unknown fields refused. Each typed `headers` or `env` value, and each `headerCredentials` or `envCredentials` value that starts with neither `secrets.` nor `mcp.`, becomes an encrypted credential `mcp.<botId>.<server>.<8 hex>` and the file keeps only the reference. A reference must be a saved `secrets.<NAME>` (a header one allowed for the server's host) or a derived key the file already had, kept by the same server and used where it was before (env stays env, a header stays on the same host); anything else is a `VALIDATION_ERROR` on `mcpServers` and the file is unchanged. Derived keys the new file no longer references are deleted; `mcp.add` over an existing name, `mcp.remove` and bot deletion delete the ones the replaced or removed entries referenced.
- MCP OAuth (`runtime/src/services/mcp-auth/`): the server URL always comes from bot config, the one-time `state` authorizes the callback browser, and `returnUrl` must be an app link or the redirect's own origin.
- Plugins are trusted native code; approval gates their tool calls, not their imports.

## Peers and subagents

Peers talk in one persistent private conversation per sender and recipient by default (`context: 'private'`; a new one starts after the sender's history is cleared); `context: 'existing'` posts into the recipient's main chat instead. Forwarding stops after three bots. Subagents cannot spawn children or contact peers. Silent answers are dropped before reaching the asking bot.

Every bot that may call `bot_ask` gets a `bots` system prompt section (`collaboration-extension.service.ts`) listing the owner's other bots with name, `[@handle](bot:<id>)` link and the `bot_list` summary (the first 280 characters of their instructions), and when to hand work over: `bot_ask` in the private context to get an answer and pass it on, `bot_message` with `context: 'existing'` when the owner wants the other bot to answer them in its own chat. A Read only bot gets neither the tool nor the section. The section only changes when bots change, so prompt caches stay warm.

The note before a delivered request (`collaborationPeerNote`) depends on where it lands and how it was sent: in the recipient's main chat it says the owner sees it and to answer the owner there; in a private chat after `bot_ask` that the reply goes back to the sender, who passes it on; after `bot_message` that the sender will not pass on details, so the recipient raises what matters with `bot_notify_owner`. The delivery task tells the two apart by comparing the target with the recipient's main conversation, so the task input did not change. Clients hide the note (`CHAT.peerNotePattern`, up to the first `]` followed by a blank line) and show the request as a *Request from @bot* notice. An approval a bot needs in a private chat shows in its main chat under *Raised from a private chat with*; the asking bot meanwhile shows *Asking @bot*.

Pi's `tool_search` is offered as `bot_tool_search` (`runtime-tool-search.extension.ts`): OpenAI's Responses API refuses a loaded function named `tool_search` (*not allowed in reserved namespace 'tool_search'*), and Pi sends tools added after a conversation started as loaded tools, which failed every OpenAI bot's first turn.

## Routines

One Pi task per routine ends each wait in a stored sleep, with no model calls (`runtime/src/services/routine/routine.task.ts`). Pi cannot wake a sleeping task early, so run-now and edits replace the routine's task in the same commit and abort the old one; a task that is delivering is left alone. A task that is no longer its routine's task ends itself. Opening a bot retries routine tasks Pi parked at its restart limit. After downtime an overdue run happens once; missed repetitions are skipped. Each store arms one host alarm at its earliest deadline, so the daemon must stay running.

## Silent replies

Assistant text that is only `NO_REPLY` or `<|eos|>` (`replySilent` in `contracts/src/types/reply.types.ts`) is hidden in chat, ignored by the chat-list preview and notifications, and dropped from peer and subagent answers. The reactions prompt asks bots to reply `NO_REPLY`.

## History clear

`conversation.clear` saves routines, todos and the latest artifact versions to `data/bots/<botId>/carry.json`, replaces the store and recreates them with the same IDs; a crash mid-way finishes on the next start.

## Notifications

- One device gets each item (reply, failure, approval, question; `notificationQueryTarget`): the most recently active open device, else the **Send notifications to** choice: *phone* is the latest-seen device with an Expo token or a Web Push subscription made on a touch device, *computer* an open computer page or else the latest-seen Web Push subscription made on a computer; the other kind when that one is missing. Muted bots notify nobody (Expo, Web Push, an open page); hidden bots notify like before.
- Presence: the web app reports `computer` and always open on a fine pointer, `phone` and open only while visible on a coarse pointer (a phone's hidden page stops running). When a device's `conversation.watchNotifications` stream ends (a closed tab or app), the daemon marks it closed until its next presence report; with several tabs of one browser a closed tab marks them all until the next heartbeat (60 s).
- Hold (`notificationActionDeliver`): an item whose target is an open page without an Expo token gets no push; it is held in `deps.held`. The page reports presence as soon as an item for it arrives (`received` in `useNotificationPresence`), which confirms it. If the page closes (stream ends), hides (presence `isOpen: false`) or sends no report within 15 s (`NOTIFICATION.holdMs`; lid closed, network lost), the device counts as closed and the item is delivered again to a target chosen afresh, usually as a Web Push. A page that closes just after confirming may get the push too: a short duplicate, never a miss.
- Web Push: each daemon makes its own VAPID key pair on first `notifications.webPushKey` and keeps it in the credentials table (`notification.web_push_vapid`). `notifications.webPush { subscription | null, platform, url }` stores the browser's subscription on its device row (`device.web_push`, JSON) and takes the same endpoint off any other device; removing the device removes it. The web app re-registers on every open, renews a subscription made with another key, and sends `null` when permission is gone. The daemon sends with `web-push`'s `generateRequestDetails` and `fetch` (TTL 1 day, urgency high, no `Topic`: FCM throttles Topic pushes to 20 per device then one per 3 minutes while answering 201; retried after 2 s and 8 s on 429, 5xx or a network error) only to a target that is not open; an open page shows the item from its watch stream instead. Payload: `{ kind, botId, title: bot name, body: the generic line, path: /rooms/direct/<handle> }`, never message text. A 404 or 410 removes the subscription. VAPID subject: the page origin when it is https, else `mailto:push@vinci.invalid`.
- The service worker (`apps/web/public/sw.js`) shows every push (Safari ends a subscription that skips one), tagged by bot id so a newer one replaces the older; a tap focuses an open window and posts `{ type: 'notification-open', path }` (`notificationWebPushOpen`), or opens the path. Opening a chat closes that bot's notifications on this device; another device's are not cleared (that would need a silent push, which Safari forbids).

## Hub

`apps/hub` is the only public origin, behind Caddy. Every request needs a `vinci_session` cookie (`<id>|<random>`, else 401 without asking) that the API's `GET /internal/session` resolves to an email; the answer is cached 5 s per token (see the Login with Vinci accounts entry in [`team-workspace.md`](team-workspace.md)). `POST /hub/password` (any identity, before the user lookup) is the person's own password change. Failures are empty 401s; a valid identity without a user is an empty 403, except for a browser page load (GET or HEAD with `Accept` containing `text/html`), which gets the hub's own static 403 page (`core-refusal.native.ts`): the signed-in email, why (no user, or not an admin), whom to ask, and a sign-out link to `/auth/logout`. An admin who is not a user loading any other page is sent to `/admin` (303). No script, `default-src 'none'`. Only `/hub/health` and the icon files `/favicon.ico` and `/img/favicon/<file>` (GET or HEAD, one segment) skip it; the icon files reach the web app without cookies or token, and anything else under `/img/favicon/` needs identity. A path with an empty or dot segment (`//rpc`, `/a//b`) is a 400 before routing.

```text
HUB_DATA_DIR/
  users.json   {"users": {"<email>": {"id", "daemonUrl", "socketPath", "advanced"?: true}}, "template": {"daemonUrl", "socketPath"}}; email, id, daemonUrl and socketPath each unique; reread within a second of a change
  admins.json  {"admins": ["<email>"]}: who may use /admin; seeded from HUB_ADMIN_EMAILS while empty or missing; written only by the hub
  pins.json    user id -> daemon server ID, written on first contact; a server ID belongs to one user only (the template's id is `template`)
  global.json  per user and settings section: follows the template (`global`) or not, and the last copy's result
```

- A missing, unreadable or invalid users.json means zero users: every identity gets 403 and the hub logs an error until the file is fixed. Fail closed, never the last good file.
- `/rpc*`, `/health`, `/files/*`, `/avatars/*`, `/embed/*` and `/mcp/callback` (HTTP and WebSocket) go to the user's `daemonUrl`; everything else goes to `HUB_WEB_URL` with the `vinci_session` cookie left in place (a daemon never gets that cookie). Client identity and forwarding headers are stripped; `X-Forwarded-Proto` and `X-Forwarded-Host` come from `HUB_PUBLIC_URL`; `Origin` passes through. A relayed `Location`, `Content-Location` or `Refresh` URL that resolves to `HUB_WEB_URL` or the daemon URL is rewritten onto `HUB_PUBLIC_URL`, so no internal address reaches the client. `/files/*` without `Authorization` gets the device token from the `bots.connection` cookie.
- An open WebSocket is rechecked every 5 s and closed (1008) once its login was ended (the API refuses the token) or its user is gone from users.json.
- Before forwarding, the daemon's `/health` must report the pinned server ID (checked at most every 5 s and on every address change), and a new pin may not equal another user's. A mismatch is a 502 and an admin-facing log line; nobody changes `pins.json` until the admin has confirmed which daemon belongs to whom.
- `socketPath` must be the real path: the hub refuses a socket that is a symlink or sits below a symlinked folder, before connecting.
- `GET /connect` without `code` mints a grant whenever the request has no `bots.connection` cookie for this user's daemon, including after `?reason=revoked|replaced`: it checks the grant's server ID against the pin and redirects to `/connect?code=<payload>`. `/hub/pair` does the same on demand. At most 5 grants per user per 10 minutes, which also ends any redirect loop. `/hub/whoami` returns `{ email, user, serverId, isAdvanced, sections: [{ id, mode }] }` (`teamWhoami` in the contracts): the pinned server ID, whether `users.json` marks the person `advanced`, and each settings section's mode (`overridden` without a record, as for the admin).
- The user app learns team mode from that answer only, never from the daemon: the web app's server function `teamRead` (SSR and every browser refetch) asks the hub's `GET /hub/whoami` with the request's `vinci_session` in hub mode (`WEB_HUB_URL`) and answers `null` without a hub; the browser never asks `/hub/whoami` itself, because a web server without a hub (the desktop app's) answers it 406. The query lives under `['team', 'whoami']` with the app's default 60-second stale time, so a changed **Advanced user** switch or section mode shows within a minute (on focus or the next screen) or on the next load. Whoami also carries the person's `name` from `hub/users.json`, which `deploy.ts apply` writes from `users.yaml` (`null` in a file written before that); the sidebar foot shows that name (the email when there is none) instead of the app name (it shows no server address in any mode). Outside the admin panel's scope the app hides the admin-managed controls with or without a hub (permission level, approval rules and timeout, secrets mode); a hub additionally hides **Settings → Server**, **Desktop** and pairing a device, and the basic sections for a person who is not advanced (`useTeam`, `settingsIsTeamVisible` in `apps/web`; the desktop app keeps those three, gotcha 318). The admin panel's scope shows everything. A section that follows global is read only (`SettingsManaged`).
- `POST /hub/sections/<section>/override` (a person, not an admin; same-origin `Origin` and a JSON or `X-Bots-Protocol` header, else 403) switches that person's section to `overridden`, exactly as the panel's **Override for this person**, and records a `sections/overridden` change row whose `by` is the person's own email. Only a person `users.json` marks `advanced` (403 otherwise), and only for `models`, `chat` and `sources` (`adminPersonSection` in the contracts; `tools` and `secrets` answer 403 too, as only the admin overrides them); an unknown section is 404, an unreadable `global.json` 503. The app's **Change it for me** calls it; the person then writes the section over their own device and a later global sync skips it. The hub never parses the daemon traffic for this: browser RPC runs over the WebSocket.
- Each daemon only receives its own user's traffic, so its peer-keyed throttles count one user's devices and hub calls together, never the whole organization.
- `/admin` and every path starting with `/admin` belong to the admin panel and never reach a daemon or a user route. They need a login whose email is in `admins.json` (else 403; 401 without a valid login). A malformed or unreadable `admins.json` means no admins, logged as an error; the hub never seeds over it. An admin who is not a user gets only `/admin*` and GET/HEAD on the web app's static files (`ADMIN_WEB_FILES` in `core-server.native.ts`: `/assets/*`; the favicon paths are public anyway); everything else is 403. `/admin` and `/admin/*` pages go to `HUB_WEB_URL` with the verified token; unknown `/admin*` paths are 404.
- Admin API (`/admin/api/*`, JSON, `Cache-Control: no-store`): `GET me` (`{ email, version }`: `version` is the hub's `VINCI_VERSION`, the only place the install's version leaves the server), `GET audit`, `GET|POST admins`, `DELETE admins/:email` (409 for the last admin), `GET|POST users`, `PATCH|DELETE users/:id` (`PATCH { name?, enabled?, advanced? }`; `GET users` items carry `advanced`), `GET users/:id/avatars/<file>`, `GET users/:id/files/<botId>/<attachmentId>[/poster]`, `POST users/:id/rpc/*` and the global settings routes below (other methods 404). Every non-GET request and every relay request needs `Origin` equal to `HUB_PUBLIC_URL` and either `Content-Type: application/json` or an `X-Bots-Protocol` header, else 403. Invalid bodies are 422. Every admin change is recorded in the audit trail (below), never bodies. With `HUB_ACCOUNTS_URL` and `HUB_ACCOUNTS_TOKEN` (required) the hub's `accounts` service calls the Laravel API's internal routes with that bearer token: `POST users` and a `PATCH` with `enabled: true` first `PUT /internal/users/{email}` `{ name }` (`{ created, password? }`), then the provisioner, and delete the account again when the provisioner fails and the account was just created; `DELETE users/:id` first `DELETE /internal/users/{email}` (skipped for an admin on the admin list), then the provisioner; `POST users/:id/password` calls `POST /internal/users/{email}/password` and returns `{ password }`. A created account's `password` rides on the `POST users` or `PATCH` reply once and is never stored or logged. An accounts failure is 502 `{ error: 'accounts_unavailable' }` with nothing changed. Each accounts call is its own audit row (`accounts/put`, `accounts/password`, `accounts/remove`, detail the email), never the password.
- Users come from the provisioner (`PROVISIONER_URL`, `Authorization: Bearer PROVISIONER_TOKEN`; the hub refuses to start with a URL and no token). The hub's `admins.json` is the one admin list: the hub sends it to the provisioner (`PUT /access/admins`) at start, retrying for about a minute while the provisioner starts, and after every admin change, so the Access allow list follows it. A failed provisioner change is logged with the provisioner's error body and answers 502. The hub derives a new user's id from the name (else the email's local part), unique against current users and every pinned id, so a new person never reattaches a kept volume. Without `PROVISIONER_URL`, user changes answer 501 `{ "error": "provisioner_not_configured" }` and `GET users` lists `users.json` with `state: 'unknown'`.
- Template workspace: `users.json` may hold `"template": {"daemonUrl", "socketPath"}`, a daemon with no email that no login reaches; its addresses count in the uniqueness check, and no user may have the id `template` (the file is then invalid). `users/template/rpc/*` relays to it like a person; it never appears in `GET users`, and a new user's id is never `template`.
- Global settings: `GET global` -> `{ sections: [{ id, procedures }], state: 'ready' | 'starting' | 'missing' }` (`missing`: no template in `users.json`; `starting`: its `/health` does not answer). Sections and their relay procedures (an entry ending in `/` is the whole area): `models` `providers/`, `models/`; `chat` `conversation/settings`, `conversation/configure` (busy mode, hide tool calls and GIFs: one procedure holds them, and the Chat tab holds all three); `tools` `tools/settings`, `tools/configure`, `transcription/settings`, `transcription/configure`; `secrets` `secrets/`, `credentials/` (the guard below lets `secrets/remove` through); `sources` the `settings` and `configure` of `skills`, `instructions`, `plugins` and `mcp`. A section procedure whose last segment is `list`, `settings` or `session` reads; every other one writes. Bot procedures are in no section.
- `HUB_DATA_DIR/global.json` `{"users": {"<id>": {"<section>": {"mode": "global" | "overridden", "sync": "in-sync" | "pending" | "failed", "error"?}}}}` is written only by the hub (whole file, in order); it is not re-read while a save is queued or writing, so a reload never drops a pending save. A user or section missing from it is `overridden` (people present before global settings keep their values). `HUB_DATA_DIR/new-users.json` `{"users": ["<id>"]}` is written only by `apply` (the people it gave a new data volume, plus any still listed in a file the hub has not consumed); every 2 seconds the hub gives each listed user with no entry every section as `global`/`pending`, copies them as a panel create does, and deletes the file if its mtime is unchanged since it was read. Unreadable or invalid means no mode can be trusted: relay writes to any person's section procedure, mode changes, `global/sync` and user creation answer 503 `{ "error": "global_state_unreadable" }` and the hub logs an error; reads still work; it recovers once the file is fixed.
- `GET users/:id/sections` -> `{ sections: [{ id, mode, sync, error? }] }`; `PUT users/:id/sections/:section { mode, marker? }` -> the same shape for that section (`global` copies the template's values in before answering, `overridden` only flips the mode). Switching an overridden section to `global` needs the `marker` of its preview: without one it answers 422, with a stale one 409, mode unchanged either way. A section that already follows global takes `{ mode: 'global' }` alone and copies again (the panel's *Try again* after a failed sync); `GET users/:id/sections/:section/preview` -> `{ section, marker, items: [{ kind, name, change: 'removed' | 'changed' | 'replaced' | 'added' }] }`, side-effect free, names only, never values (kinds: `provider`, `chatSetting`, `toolSetting`, `secret`, `secretSetting`, `skill`, `instruction`, `plugin`, `mcpServer`, `file`, `sourceSetting`; the Secrets preview skips the person's own secrets and lists one with a global secret's name as `replaced`), 404 for the template, an unknown or disabled person, 502 when either daemon does not answer; `GET global/status` -> `{ users: [{ id, sections }] }`; `POST global/sync { section? }` copies that section (or all) to everyone who follows it and answers with the status. Unknown user or section: 404.
- A relay write to a person's daemon on a section in mode `global` is 409 `{ "code": "SECTION_FOLLOWS_GLOBAL", "section" }`, except `secrets/remove`, so the admin can remove a person's own secret; the panel offers it only for secrets without `isGlobal` there, and a global one removed through the API comes back with the next copy. A successful relay write to the template on a section copies that section to every person in mode `global` in the background; saves that land during a copy run it once more, so the last save reaches everyone. Copies to one person run one at a time, and a multi-section copy reads each section's mode again just before copying it, so an override saved meanwhile is skipped and kept; switching a section to `overridden` waits for a copy already running for that person, so nothing written after the switch is overwritten; one failing daemon does not stop the others. A person without a running daemon (disabled) stays `pending`; enabling them (`PATCH users/:id { enabled: true }`) copies every section they follow. A failed copy stays `failed` with the error until the next sync.
- A hub start runs the same copy as `global/sync` for every section in the background (`global.actions.start`) unless the start sync of this version already ran (`hub/start-sync.json` with `HUB_VERSION` and its audit row id, gotcha 197), then retries each person's failed sections every 2 s, 30 attempts, and records one `global/sync` audit row with `admin` `hub start` (status 200, or 503 when `global.json` is unreadable).
- A copy reads the template and writes the person with the forms' procedures, plus the owner-socket-only exports for what the forms cannot read: `models` is `providers.export` then `providers.import`, then `models.settings` into `models.configure`; `chat` `conversation.settings` then `configure`; `tools` the settings plus `tools.export` into `tools.configure`, then `transcription.export` into `transcription.configure`; `secrets` the mode, then `secrets.export` into `secrets.import`, which keeps the person's own secrets; `sources` replaces the contents of `~/.agents` with `workspace.export`/`import` (the folder itself stays, since the sandbox mounts it: entries are swapped by rename, folders both sides have entered), then copies the four path lists. Values cross the hub in memory only; it never logs or stores them.
- `POST users { name, email, bots? }` sets every section of the new person to `global`, copies them, then copies the listed template bots before answering; the reply gains `bots: [{ from, botId | null, error? }]`. `POST users/:id/bots/copy { bots }` -> `{ bots: [...] }` later. A copy is `bots.get` and `bots.exportFiles` on the template, the avatar image fetched from the template's public `/avatars/<id>.webp` and uploaded with `avatars.upload`, `bots.create` with the same fields (a new id; a taken handle fails that copy), then `bots.importFiles`, deleting the new bot if that fails, so a failed copy leaves nothing behind and can be retried; derived MCP header values travel only to someone whose `secrets` section is `global`.
- `users/:id/rpc/<procedure>` relays HTTP to that user's owner socket at `/rpc/<procedure>` (the private door). The procedure must be plain path segments (`[A-Za-z0-9]`, no encoding) and never `pairing/*`, so no admin can mint a device, nor one of the owner-socket-only export and import procedures, so no secret value reaches a browser. Only `Content-Type`, `Accept` and `X-Bots-Protocol` are forwarded; the hub sets `X-Bots-Server-Id` to the pinned server ID, so a socket that belongs to another daemon refuses the call. Origin, cookies (the login's too) and `Authorization` never reach the socket. Replies carry only `Content-Type` and `Content-Disposition`. The owner socket checks (real path, is a socket, no symlinked folder) are shared with the pairing hand-off.
- Relayed reads that return a person's content are audited: `conversation/list|history|search|questions`, `tools/pending`, `artifacts/get`, `routines/list` and `todos/list`. The hub accepts them only as an `application/json` body with a `Content-Length` of at most 64 KiB (it never buffers more) that it parses (`{ json: { botId, conversationId? , … } }`; `conversation/list` takes no input), answers 422 to anything else (multipart, form data, broken JSON, no `botId`), and forwards exactly the bytes it parsed without the query string, so the line always names what the daemon serves. Each call writes one audit row of kind `read` (below) with the user, `botId` (`null` for `conversation/list`, which reads every bot's chat with its last-message preview) and `conversationId` (`null` for the bot's main chat); never the query, the reply or any other field. `conversation/reactions` and `artifacts/versions` get the same body rules but no row (they return only emoji on entries the admin read through an audited history call, and version numbers and dates). `tools/pending` and `conversation/questions` write their row only when the daemon's reply lists something: the hub reads that reply (a non-OK one, or one it cannot parse as an empty `{ "json": [] }`, still writes a row) and forwards the same bytes, so opening a chat where nothing waits adds no row. Relay calls the forms make on every load (a last segment of `list`, `get`, `catalog`, `settings`, `discover`, `shared`, `local`, `state`, `info`, `status` or `session`) keep the `Admin call relayed to a private door` line and no row; every other relay call is a change.
- `users/:id/files/<botId>/<attachmentId>` and `…/<attachmentId>/poster` (GET, admins only, `template` too) read that attachment through the person's owner socket (`attachments.download`, `attachments.poster`), never the public door; both ids must be UUIDs, else 404, and the daemon answers 404 for an attachment that is not in that bot's chat. `Range` is passed on (206 or 416 as on the daemon's `/files`). Replies carry only `Content-Type`, `Content-Disposition`, `Content-Range` and `Accept-Ranges`, plus `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox; default-src 'none'`; only PNG, JPEG, WebP, GIF, video and audio stay `inline`, every other type (SVG, HTML, PDF, text) is sent as `attachment`. A file opened in a tab therefore never runs as the panel. The route takes a plain GET (`<img>`, `<video>`) with no Origin or protocol header, like the avatar route; the hub adds `X-Bots-Protocol` and the pinned server ID itself, and refuses a request with `Sec-Fetch-Site: cross-site` (403) before reading or auditing. A reply that starts at byte 0 (no `Content-Range` from the daemon, which covers a missing or unparsable `Range`, or one starting `bytes 0-`, which covers a suffix range reaching the start) writes an audit row; later ranges of the same file (a video playing) and a 416 do not. The hub decides from the daemon's reply, not the request header.
- Audit trail: `HUB_DATA_DIR/audit.sqlite` (`bun:sqlite`, rollback journal, `synchronous = FULL`, mode 0600), one append-only table `audit` (`id`, `created_at`, `admin`, `kind` `read|change`, `action`, `detail`, `user_id`, `bot_id`, `conversation_id`, `status`), created with `CREATE TABLE IF NOT EXISTS` at start. Reads are the audited relay reads, the files route and `outside/load`; `action` is the procedure. Changes are `admins/add|remove` (`detail`: the email), `users/create` (`detail`: the email; `user_id` once created), `users/update|enable|disable|remove`, `users/advanced` (`detail`: `on` or `off`), `sections/global|overridden` (`detail`: the section; `sections/mode` when the body was invalid), `global/sync` (`detail`: the section or null), `bots/copy` (`detail`: how many), and every other relay call, `action` the procedure and `bot_id` the body's `json.botId` when the body is JSON of at most 64 KiB (the hub then forwards the bytes it read); nothing else of a body is kept. `status` is the reply's, or the mapped status of a thrown refusal (a refused relay procedure is a `change` with 403). Every row is also logged as a `hub-audit` line (`Admin read a conversation`, `Admin read routines or todos`, `Admin made a change`) before the insert. A read whose row cannot be inserted is refused: 503 `{ "error": "audit_unavailable" }` (an empty 503 on the files route) after the daemon answered, its body discarded. A change whose row cannot be inserted keeps its answer and logs an error. `GET audit?cursor&by&user&kind` -> `{ entries: [{ id, createdAt, by, kind, action, detail, userId, botId, conversationId, status }], next }`, newest first by `id`, 50 per page, `next` the `cursor` for the following page (`null` at the end); unknown or invalid parameters are 422, other methods 404, and reading it writes no row. An audit file that cannot be opened (damaged, unwritable) never stops the hub: it logs an error at start, every row fails as above, and the open is retried on each use. `purge` leaves the file alone.
- `POST users/:id/outside { botId, conversationId }` (strict body, else 422; `template` too, an unknown id 404) records that the admin chose to load outside content in that conversation: one `read` row `outside/load` (`Admin loaded outside content in a conversation`), then 204. It reads and forwards nothing. When the row cannot be written it answers 503 `audit_unavailable` and the panel loads nothing.
- `users/:id/avatars/<file>` serves that user's `/avatars/<file>` (`<uuid>.webp` or `bots/<uuid>.png`, else 404; `template` too) from their pinned daemon with `Cache-Control: private, no-store`, never the daemon's public caching, because the hub routes `/avatars/*` by the viewer's own identity. The panel's per-user RPC context maps `/avatars/…` image sources there at display time (`avatarSrc`); stored avatar values never change.

## Bot start and the model for new bots

- Every `bots.create` adds a `bot_start` row, whoever calls it (a device, a bot's own `bot_create` tool, the hub's suggested-bot copy, the admin panel's relay, a by-hand call) and with or without instructions; `bots.update` never starts a bot. `bots.open` (devices only; the owner socket refuses it) is called by the chat screen each time a bot's main chat mounts: with a `bot_start` row it runs the start turn (`bot.prompts.ts`: introduce itself, do immediate work, create missing routines; without instructions it asks what to do) if the conversation is empty, then deletes the row, in the bot's queue so two devices start it once. So every bot greets the first time its person opens it, and no model runs before then.
- Each request stamps every user message with the time it was sent, in the person's timezone (`bots.clock` extension, Pi's `beforeRequest` hook; nothing is stored). The stamp comes from the message's own timestamp, so the request prefix and the system prompt stay the same and provider prompt caches stay warm. Devices send their IANA timezone with `conversation.submit`; the daemon keeps the last one in the `person.timezone` setting and falls back to its own timezone.
- `models.settings` -> `{ defaultModel: { modelProvider, modelId, thinkingLevel, fallbackModel } | null }` and `models.configure` with the same shape store the model a new bot's form starts with (setting `bots.defaultModel`, JSON). Nothing checks that the model exists: the web create form (`botNewModel` in `client/src/services/bot/bot.utils.ts`) uses it only when `models.list` offers it (and its fallback only when offered too), else the newest model as before. Served on the owner socket; in the Models section of global settings. Only the admin panel shows the field; the person's app never sets it.
- The web create form starts with `inherit` including `agentsFile` (**Also read the shared instructions**) everywhere: the person's app and the admin panel. The server's `botCreate` default is unchanged, and a suggested-bot copy sends the template bot's own `inherit`.
