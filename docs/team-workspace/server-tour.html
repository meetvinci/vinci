What runs on the Orbs team server, and how to change a bot by hand

Six levels, from the machine down to one line of a bot's instructions. Every terminal block is real output from the test install with the first admin panel version (7c0f545). Emails are shown as <email> and secrets are masked. Since the global settings upgrade the server also runs orbs-daemon-template-1, and the demo person tourdemo and the tour-capture container are gone; to try the editing examples, add a throwaway person in the admin panel and use its id.

your Mac
ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes root@[REDACTED]
cd /opt/orbs

Every server command below runs as root in /opt/orbs. SSH is allowed only from your current IP address.

1The server

The server is an Ubuntu 24.04 machine with Docker. Everything Orbs-related runs in containers. Bun is installed on the host only to run deploy.ts, the script that applies changes, backs up and restores.

Nothing Orbs-related listens on a public address. The Cloudflare connector dials out, so the tunnel is the only way in. The two 172.17.0.1 lines are test-only stand-ins for a model provider, reachable only from containers on this machine.

Secrets are not readable

A secret saved through the app or the door is stored encrypted. The database holds only ciphertext; the name and the allowed hosts are visible, the value is not.

the demo secret, as stored
$ ... select key, length(value) as cipher_chars, length(iv) as iv_chars from credentials ...
[ { key: "secrets.TOUR_DEMO", cipher_chars: 60, iv_chars: 16 } ]

5Three ways to change a bot without the app

All examples act on the demo person tourdemo and its bot tour-bot. Its model is a small test stub that answers with the marker words it received, which shows exactly what reached the model.

Edit a file

Write as user 1000, the user the daemon runs as, so the daemon can still read the file. The daemon reads the instructions file before every message, so the change applies at once.

change the instructions file, then chat
$ docker run --rm --network none --user 1000:1000 -v orbs_data-tourdemo:/data --entrypoint sh orbs-daemon:$TAG -c \
  'printf "# Tour instructions\n\nAlways greet with MARKER_EDIT_102041.\n" > /data/agents/<botId>/AGENTS.md'
you> hello after editing AGENTS.md
tour-bot> capture via claude-haiku-5-5 ... MARKER_EDIT_102041

A skill takes up to 30 seconds, because the daemon caches each bot's skill list for that long. An MCP server added to .agents/mcp.json is started on the next message:

an MCP server added by hand, then used by the bot
$ cat /data/agents/<botId>/.agents/mcp.json
{"mcpServers":{"tour":{"command":"bun","args":["/data/agents/<botId>/.agents/tour-mcp.js"]}}}
you> CALLTOOL: what time is it on the server?
tour-bot> the MCP tool answered: "2026-11-12T10:21:18.488Z"

Call the private door

The private door is a socket file inside each person's workspace. It accepts the same requests the app makes for settings and bots, and refuses chat, approvals and pairing. The admin panel uses this same door through the hub.

list a person's bots
$ docker compose exec -T daemon-tourdemo bun -e 'const r = await fetch("http://localhost/rpc/bots/list", { method: "POST", unix: "/data/data/ipc/rpc.sock", headers: { "content-type": "application/json", "x-bots-protocol": "1" }, body: JSON.stringify({ json: {} }) }); console.log(r.status, await r.text())'
200 {"json":[{"avatar":null,"name":"Tour Bot","handle":"tour-bot","modelProvider":"anthropic","modelId":"claude-haiku-5-5","thinkingLevel":"low","permission":"full",...}]}

To change a bot, call bots/update with only the fields you want changed. The daemon checks the values, saves them and reconfigures the bot, so the next reply uses them.

change model and instructions through the door
$ door tourdemo bots/update '{"botId":"<botId>","instructions":"You are the tour demo bot. MARKER_DOOR_102121","modelId":"claude-sonnet-5-5"}'
200 {"json":{...,"instructions":"You are the tour demo bot. MARKER_DOOR_102121","modelId":"claude-sonnet-5-5",...}}
you> hello after the door change
tour-bot> capture via claude-sonnet-5-5 ... MARKER_DOOR_102121

door is the command above wrapped as a small shell function; the tour script defines it.

The door refuses anything that would act as the person:

refused on the private door
conversation/history   403 FORBIDDEN
conversation/submit    403 FORBIDDEN
pairing/create         403 FORBIDDEN
routines/create        403 FORBIDDEN

What not to do

  • Do not edit app.sqlite while the daemon runs. A hand edit skips the daemon's checks. One invalid value made the person's whole bot list fail until the row was put back:

    tried on the demo person, then reverted
    $ sql "update bot set permission = 'banana' where handle = 'tour-bot'"
$ door tourdemo bots/list
500 {"json":{"code":"INTERNAL_SERVER_ERROR","message":"Output validation failed"}}
$ sql "update bot set permission = 'full' where handle = 'tour-bot'"
$ door tourdemo bots/list
200 {"json":[{"avatar":null,"name":"Tour Bot",...

  • Do not write to runtime.sql. The daemon recovers conversations, approvals, routines and todos from it on every start. A hand edit breaks that recovery for the bot.

  • Do not delete daemon.lock. It does not stop the daemon. It only lets a second process open the same files and corrupt them.

  • Do not edit users.compose.yaml or hub/users.json. They are regenerated. Edit users.yaml, then run bun deploy.ts apply.

When something cannot be changed through the door, take a backup first with bun deploy.ts backup <id> and edit only while that person's daemon is stopped.

6How a request travels

A person opening the app:

The hub sends the app's data paths (/rpc, /files, /avatars and a few more) to the person's daemon and every other path to the shared web app. Without a valid Cloudflare signature it answers 401:

asking the hub directly, with no login
$ docker run --rm --network orbs_tunnel --entrypoint bun orbs-hub:$TAG -e 'for (const p of ["/rpc", "/admin", "/hub/health", "/favicon.ico"]) { const r = await fetch("http://hub:47192" + p, { redirect: "manual" }); console.log(p.padEnd(14), r.status) }'

/admin         401
/hub/health    200

An admin changing a person's bot from the panel:

Admin panel/admin, in the web app
→
hubis this email in admins.json? logs who did what
→
private doorthe socket of that person's daemon

The admin never becomes a device of the person. The hub relays one request at a time over the socket and writes a log line for each.

+Cheat sheet

on the server, in /opt/orbs
docker compose ps                              # containers and health
docker stats --no-stream                       # memory and CPU

# edit a file in a workspace as the daemon's user
docker run --rm -it --network none --user 1000:1000 -v orbs_data-<id>:/data --entrypoint sh orbs-daemon:$TAG

# the private door: bots/list, bots/update, bots/catalog, secrets/list, routines/list
docker compose exec -T daemon-<id> bun -e 'const r = await fetch("http://localhost/rpc/bots/list", { method: "POST", unix: "/data/data/ipc/rpc.sock", headers: { "content-type": "application/json", "x-bots-protocol": "1" }, body: JSON.stringify({ json: {} }) }); console.log(r.status, await r.text())'

docker compose restart daemon-<id>             # after changing pi/models.json
bun deploy.ts apply                            # after editing users.yaml
bun deploy.ts backup <id>                      # before any risky change

!Found on the way

  • A pairing PIN in the logs. A daemon that starts with no paired device prints a working PIN in its container log for five minutes. Reading it needs server access and using it needs that person's Cloudflare login, so the risk is low, but a team install never needs it.
  • A possible gap with MCP tools. After the bot discovered an MCP tool, later requests still did not carry that tool's description, though calling it worked. Seen only with the test stub; it needs a check with a real model.
  • One unexplained refusal. When the second person logged in, their daemon refused one pairing call half a second after the hub issued the grant. The login worked. Not yet investigated.
  • Log noise. Each daemon warns about a missing shared skills folder on every message for people who have none.
